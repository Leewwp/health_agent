## 3. 主流程结论

上一轮三个批次的**核心契约绝大部分真实生效**：七字段简报与未支持偏好诚实登记、可补充项契约与 chip 收敛、无确认简报按钮、推荐前预检与"开始推荐"同名确认短语、生成说明两分区（计划页 + 详情/版本 API + DB metadata）、显式任务路由、难度冲突与严格候选、浏览页 facet/三餐/搜索/收藏、会话持久化、跨域恢复、移动端无溢出、旧链路字段兼容——均通过真实浏览器与 API 交叉验证。

**但存在一个阻断性缺陷使"带偏好的餐食推荐"这一最高频主流程整体失效**（见 4.1），且该缺陷在当前数据下是确定性复现（不是偶发），与 2026-08-29 验收记录（"点击开始推荐→2 张餐食推荐卡"）直接矛盾，需要立即修复。

## 4. 发现的问题

### 4.1 【P0】健康链餐食推荐：餐次以外的任何偏好维度 → 稳定 0 候选（主推荐流程失效）

- **复现**：新会话（无历史槽位）输入"推荐清淡的晚餐"或"今晚想吃得清淡一点，有什么推荐？"或"想喝点清淡的粥"→ 回复"当前条件下没有严格匹配结果。你可以在原条件上追加以下可用选项：追加健康目标：低油/均衡/控碳水"，无候选、无预检、无卡片。
- **数据佐证**：MySQL 中 5 条 `healthGoal` 含"清淡"的 APPROVED 公共餐食（清蒸鱼 2425、快手清蒸红鲷鱼 2380、柠檬腌梅蒸鲳鱼 2392、姜丝蒸虾 2570、香菇酱油鸡 2584）均存在且含晚餐/三餐；`mealTime=晚餐&foodType=轻食` 浏览 API 返回 20 条；同输入走旧链 `/api/v1/diet/chat` 返回 3 张卡。数据面无问题。
- **根因链**：
  1. 健康链结构化检索 `StructuredMealRetriever.hardRecallSlots()` 只把 `mealTime` 传给 SQL 召回，其余维度（healthGoal/taste/cuisine/foodType/convenience）不进入召回谓词；
  2. 召回 SQL `ORDER BY updated_at DESC LIMIT 50` 截断到 50 条，无次排序键——而 `ReviewedResourceSeeder` 每轮启动把 295 行 `updated_at` 刷成同一秒，`LIMIT 50` 取到的是执行计划决定的无序子集（本轮恰好不含任何"清淡"行）；
  3. 随后 `MealModule.matchesStrict()` 在 50 条内做全维度 AND/OR 过滤 → 恒 0。
  4. 2026-08-29 验收能返回 2 张卡属同一次序下的运气（当时 50 条窗口内含清淡行）；`f8b9bc5` 重新生成 seed 后窗口内容变化，缺陷被稳定暴露。**行为是非确定性的**：同一输入在不同数据快照下时而 2 卡、时而 0 卡。
- **真实影响面**：
  - 用户带任何偏好词（清淡/粥/辣/川菜/素食…）的餐食推荐全部 0 候选，只落入"追加可用选项"兜底；
  - 推荐前预检（v3.2 核心）在这些场景不可达（预检要求候选非空）；
  - 而 `MealModule` 的严格过滤与"向量不绕过硬约束"契约是**故意的**（有注释与测试），缺陷在召回侧，不在过滤侧。
- **修复方向（一线）**：把 `hardRecallSlots` 改为将全部显式槽位传给 `DbReviewedMealReader.recallStructured`（其 SQL 已完整支持 7 维 JSON_OVERLAPS，浏览/计数路径已按 f8b9bc5 的"合并唯一检索语句"设计）；并将召回排序加确定性 tiebreaker（如补 `id DESC`），消除同秒 `updated_at` 下的随机截断。改后应与浏览 API 词表严格一致（正是 meal-facet-repair 规格承诺的"审核库推荐与浏览共享同一词汇"）。

### 4.2 【P1】跨轮槽位继承使"换主题推荐"被旧偏好卡死

- **复现**：同一会话先问"推荐清淡的晚餐"（healthGoal=清淡 存入会话），下一条"中午吃什么"→ `SLOTS_MERGED` 合并出 `{mealTime:[午餐], healthGoal:[清淡]}` → 同样 0 候选。
- **说明**：槽位合并本身是会话语境设计，但用户换主题时旧偏好无显式出口；配合 4.1 的召回缺陷，两个问题叠加后"会话内任何后续推荐"都失效。修复 4.1 后此问题会大幅缓解（候选非空），但建议评估"换主题"时是否应弱化历史偏好（如仅保留餐次维度）或给出清空入口。

### 4.3 【P1】训练"候选不足"说明未达用户可见

- 规格 #108："唯一候选按指定训练日复用并在生成说明中明确候选不足"。
- 实现：文案存在于 `TrainingPlanGenerationService.deterministicExplanation()`（"符合全部条件的候选动作只有 1 个，不足以为每个训练日安排不同动作，已按指定训练日复用候选。"），存于计划 explanation 字段；但 `frontend/assets/js/pages/plans.js` **不渲染 explanation**，计划页/生成说明两分区只渲染 generationNotes（未支持偏好 + 按日回退）。训练唯一候选复用（2-5 场景真实发生）时用户看不到任何候选不足提示。
- 修复方向：把候选稀缺说明并入计划页生成说明（如 generationNotes 增加 `candidateScarcity` 字段或前端渲染 explanation），并补充自动化断言。

### 4.4 【P2】餐食计划整周回退 + 能量下限 → 生成后无法直接激活（已知边界复现）

- 复现：偏好组合（川菜+素食+清淡+快速）无候选 → 整 7 天回退生成 21 项；其中 5 天每日热量低于 1950 kcal 下限 → 确认（UNENABLED）可以，激活被拒（toast"当日餐食估算热量超出推荐区间，激活前建议先调整。"）。
- 2026-08-11 已记录同类边界（"自动生成草稿可能因四舍五入/组合低于能量下限而无法激活"）。本轮在"整周回退"路径下再次命中，且回退本身是 4.1 修复后也应保留的诚实行为。建议：回退组合时把"每日能量落入档案区间"纳入回退约束（或回退说明中给出热量提示），至少让计划可直接激活。

### 4.5 【P2/观察】训练简报卡两组 chip 文案不一致

- 澄清阶段的缺失槽位 chip（训练目标/训练部位/器械/难度/训练日/训练时段）与可补充项 chip（训练目标/训练部位/器材/难度/训练日期/训练时段）同时显示、内容重叠但措辞不同（器械 vs 器材、训练日 vs 训练日期、训练时段 vs 训练时段）。餐食简报无此问题（两组一致或互补）。属文案层不一致，建议统一为同一词语（HealthSlotLabels 与 supplementable label 共用一份词表）。

### 4.6 【信息】计划 `planScope` 全部为 COMPOSITE 属设计而非缺陷

- 生成链路（餐食-only/训练-only/综合）落库 `planScope=COMPOSITE`（`WeeklyPlanService.persistScopedGeneratedDraft` 显式设置，注释"用户侧统一看作综合周计划"），与 `.scratch/health-agent-unified-plan-editor/spec.md`"所有新计划统一保存为可容纳餐食和动作项目的综合周计划"一致；V15 的 EXERCISE/MEAL 枚举仅对不经过统一生成入口的旧/手工路径保留。已在内容层面验证隔离（餐食计划 21 项无动作、训练计划 2 项无餐食）。**无需修复**，但 AGENTS.md 关于"EXERCISE/MEAL/COMPOSITE scope isolation"的表述与运行行为存在字面张力，建议补一句说明。
