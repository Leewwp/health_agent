# 健康 Agent 两阶段交付边界

日期：2026-08-28

本文把项目拆成两个不同目标，避免把面试演示原型和长期产品路线混为同一验收门槛。

截至 2026-08-28，[#102 训练计划与跨品类交互修复](https://github.com/Leewwp/health_agent/issues/102) 已完成实现、自动化测试和真实浏览器验收，规格状态为 `ready-for-human`，GitHub issue 保持 OPEN 等待人工审阅。

## 第一阶段：面试与简历 MVP

目标是本地可运行、页面可浏览、Agent 主流程可演示。安全边界以“确定性约束优先、无法满足时明确拒绝或请求追加条件”为准，不追求生产级个性化和云端运维。

必须跑通：

- 餐食单次推荐和动作单次推荐；
- 严格匹配训练部位、器材、目标和难度，结果去重；
- 聊天推荐同一槽位多值使用 OR、不同槽位使用 AND；无结果时只展示能产生候选的追加值，用户点击后才扩大范围；
- 推荐卡片和计划资源选择器可查看餐食/动作详情；
- 健康档案保存、缺档案时回到原聊天位置；
- 训练、餐食、综合计划需求简报、预览、生成草稿和启用；
- 综合计划一次性生成餐食与训练，任一部分失败则不落库；
- 训练计划覆盖全部指定训练日；候选足够时一周内动作不重复，候选不足时按最少重复原则复用以保证流程生成；
- 我的计划查看、草稿复核、启用，以及新增/替换项目时的详情弹窗；
- 本地启动命令、固定夹具降级和真实浏览器主流程验收。

第一阶段不把候选稀缺做成复杂优化问题：只要存在可用严格候选就继续生成；复用不设硬次数上限；极端无法排程属于小概率，不增加专门兼容分支。

## 第二阶段：长期优化（Future Work）

以下内容不阻塞面试 MVP：

### 第二轮优先收口（审计确认未完成）

- 浏览页筛选和“我的计划”资源选择器支持同字段多选 OR，并同步扩展 HTTP 参数、Reader、MyBatis SQL、分页计数与前端测试；
- `MealPlanBrief` 保存菜系、口味等多值偏好，综合计划中“中餐和西餐”等输入进入预览摘要、候选筛选、版本快照和生成结果；
- 为 M1-M9 fixture 补齐可验证的多维标签，或在 UI/文档中明确它仅支持餐次维度，不能把 fixture 结果当作正式库严格筛选证据；
- 当前启用计划除当天项目外，补充计划目标软上下文及显式来源提示；本轮明确输入始终优先；
- 明确训练“部位”筛选究竟按源主部位/目标肌群，还是继续包含辅助肌群；当前 `bodyParts` 聚合三者，因此“练胸”可能召回主部位为背、胸仅为辅助肌群的动作，调整前必须同步 Provider 契约、推荐文案和回归样本；
- 增加详情抽屉快速切换 A/B 的前端自动化回归，并完成移动端训练、餐食、综合计划的完整交互复验；桌面三种计划的简报预览、生成、草稿复核、启用已于 2026-08-28 走通，`390×844` 当前综合计划只完成布局与溢出检查；
- 使用目录中确有严格候选的五日训练简报完成训练、餐食、综合计划生成、草稿复核、启用；无严格候选时验证明确拒绝而非错误生成。
- #102 已从第二阶段移出并纳入第一阶段主流程：餐食/综合计划只生成用户选择的餐次，按所选餐次归一化分配热量，候选足够时跨日优先换餐、候选不足时最少重复；训练澄清、训练 Guard、训练去重和 picker 详情/反馈修复均已完成。

- Agent 通过自然语言直接添加、替换、删除或移动已保存计划项目；
- 更复杂的多轮意图仲裁、长期偏好记忆和个性化重排；
- RAG 准确率、评测集、向量基础设施和多阶段 rerank 的持续优化；
- 全量动作计划资格审核、复杂训练处方、周期化与高级恢复规则；
- 更丰富的餐食/训练新品类和指南检索；
- 云部署、HTTPS、生产账号、运维和多实例架构；
- App、原生桌面端、打卡、提醒和长期行为追踪。

第二阶段能力不得通过放松第一阶段的硬约束来实现，必须建立独立测试、数据契约和验收证据。

## 验收口径

第一阶段的“完成”以本地浏览器能完整走完推荐、档案回跳、训练/餐食/综合计划生成和启用为准；第二阶段只记录为路线图，不计入面试交付承诺。当前唯一术语为“当前启用计划”，本轮明确需求优先于该计划提供的软上下文。
