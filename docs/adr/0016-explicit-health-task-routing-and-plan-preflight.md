# 健康聊天显式任务路由与计划生成前预览

Status: accepted

## Context

健康 Agent 同时覆盖餐食、健身和作息。历史实现允许模型或槽位在新会话中猜测领域，也把计划简报确认、推荐前确认和计划生成混在同一条状态链中，导致作息问题返回餐食资源、训练计划候选越过部位约束，以及用户看不懂或没有见过的确认阶段阻断生成。

现有资源读取、风险 Guard、计划生命周期和类型化资源边界已经稳定；本决策只收敛对话入口、简报预览和候选约束，不引入新的资源系统或数据库模型。

## Decision

1. 新会话只有明确任务词进入餐食推荐、训练动作推荐、餐食计划、训练计划或综合计划。模糊短句进入 `OTHER + CHAT` 或领域澄清；活动澄清上下文允许短句继承当前领域。
2. 显式切换领域暂停旧计划简报而不清空；当前领域的槽位投影是澄清、检索和资源展示的唯一输入，明确继续表达才恢复旧简报。
3. 计划简报只作为用户可见摘要和补充入口。移除独立的“确认简报”按钮、确认文案、确认阶段和确认版本依赖。用户点击“开始生成”时，服务端校验当前简报完整性并直接创建草稿；请求幂等、风险和资源事实重读继续保留。
4. 推荐前预览使用“开始推荐/补充”，不使用“确认推荐”。餐食最低条件和健身四项必填条件保持不同，不因统一文案而改变领域语义。
5. “全身”只匹配动作资源明确归一的全身标签；零候选不自动放宽，唯一候选允许按指定日期复用并明确说明。难度是单选，多值冲突保留已有值并提示只能选择一个难度。
6. 作息本轮沿用已核验的结构化事实。未来可评估文档证据和 RAG，但无证据时不编造固定停止锻炼时间。
7. 浏览页名称搜索由可管理的事件委托负责，回车必须阻止文档导航并发送 `q`；跨页面切换不能累积旧监听器。

## Alternatives considered

- 继续让 LLM 猜测新会话领域：实现简单，但错误会直接造成跨品类资源泄漏，无法通过结果 Guard 可靠补救。
- 保留独立简报确认：看似安全，但用户无法理解，且与“开始生成”重复，曾造成餐食流程被确认状态阻断。
- 全身放宽为任意单部位动作：可以提高候选数量，但违背用户硬约束且无法解释腿部/背部动作为何满足全身。
- 零候选自动去掉目标或难度：能提高生成成功率，但会静默改变用户需求；改为显式追加/修改条件。
- 立即接入作息 RAG：范围和评估成本独立于本轮回归，可能把路由修复与证据系统变更耦合，延期处理。

## Consequences

- 对话状态更少且可见操作更直接，跨域错误和隐藏确认阻断减少。
- 服务端仍需在开始生成时执行完整性、风险、资源和幂等校验；删除确认字段可能需要兼容旧会话读取和停止写入。
- 严格全身语义可能暴露动作数据覆盖不足，系统必须诚实返回零候选或唯一候选复用。
- 前端需要新增跨路由事件生命周期测试和真实浏览器 Network 验收。
- 作息能力短期仍是结构化事实，文档/RAG 作为独立后续研究任务。
