# Agent MVP 面试适用性复核

- 日期：2026-08-10
- 复核对象：当前饮食 Agent 代码、健康 Agent 正式规格、31-36 号实施票据
- 目标：在不追求生产级医疗系统的前提下，交付功能可运行、边界可解释、失败可降级、结果可验证的最小实现

## 结论

当前方案的技术方向适合 Java 后端与 Agent 开发面试，但原实施顺序不适合最小实现：资源 ETL、媒体审核和 RAG 被安排在多品类 Agent 编排之前，任何数据准备阻塞都会导致项目长期没有新的 Agent 主流程可演示。

本轮调整后，实施顺序改为：先验收基础设施，再用小型审核种子资源跑通 Agent 垂直闭环，然后增强正式资源和餐食 RAG，最后补周计划、前端与发布证据。这样既保留完整 MVP 目标，也能在中途形成可用的面试演示版本。

| 维度 | 调整前 | 调整后判断 |
|---|---|---|
| Agent 职责边界 | LLM 与 Java 分工基本正确，但调用依赖具体 `ReActAgent` | 增加统一 Agent 运行接口和固定夹具适配器，可测试、可离线演示 |
| 最小可交付性 | 资源和 RAG 阻塞健康编排 | 31-32 完成后即可演示三品类对话、降级和 Trace |
| Agent 技术含量 | 有多角色 Prompt 和状态机，但容易被误解为普通 LLM 串联 | 明确结构化契约、输出校验、候选约束、降级分类和评估集 |
| 面试可信度 | 规划内容多，完成证据后置 | 每张票自带测试/冒烟证据，最终票只汇总而不补救 |
| 范围风险 | 全量资源、媒体与完整页面同时进入首版 | 使用审核子集和稳定无图状态，扩量不阻塞闭环 |

## 适合保留的设计

1. `HealthOrchestrator` 管理状态和路由，Agent 不直接写数据库或控制状态转换。
2. `IntentAgent` 处理自然语言中的跨品类意图、槽位和明示偏好，Java 负责合法值、风险和低置信度修正。
3. 响应 Agent 只能解释已排序候选或已校验计划，不能创造资源 ID、数值、剂量、风险结论和来源。
4. 餐食 RAG 只负责候选召回，硬约束过滤和最终排序仍由 Java 完成；Embedding 失败时回退结构化检索。
5. 周计划由确定性组合器生成并校验，LLM 只做表达。这比“让 LLM 自由生成一周计划”更适合健康场景，也更容易在面试中论证。

## 必须补强的 Agent 设计

### 1. 隔离 AgentScope

现有业务服务直接依赖 `AgentFactory` 和 `ReActAgent`，固定测试只能绕过整个调用层。实施时应在外部模型依赖处定义一个小接口，例如 `AgentInvoker`，并提供两个真实用途明确的适配器：

- `AgentScopeInvoker`：生产/开发环境调用 DashScope；
- `FixtureAgentInvoker`：自动化测试和离线演示返回版本化固定结果。

接口只传递 Agent 角色、会话、超时预算和输入载荷，返回原始输出、模型信息和耗时。Prompt 组装、JSON 解析、DTO 校验、候选 ID 校验、Trace 和降级由内部的 Agent 契约模块统一完成，不向业务模块暴露 `ReActAgent`。

### 2. 固定结构化契约

每个 Agent 契约必须具有 `contractVersion`、`promptVersion`、输入 DTO、输出 DTO 和校验器。非法 JSON、缺字段、未知枚举、候选越界和超时都返回类型化失败原因，不使用空 catch 隐藏原因。

Trace 至少记录：Agent 角色、模型、Prompt/契约版本、耗时、解析状态、候选 ID、最终引用 ID 和 `fallbackReason`。健康档案等敏感输入只记录摘要或脱敏值。

### 3. 诚实描述“多 Agent”

本项目是**确定性编排的多角色 Agent 工作流**，不是让多个自治 Agent 自主规划和调用工具。四个角色可以沿用，但只有以下调用具有明确价值：

- `IntentAgent`：解决跨品类语义理解；
- `RecommendResponseAgent`：解释受约束候选；
- `PlanResponseAgent`：解释已校验计划。

`ClarifyAgent` 只优化追问措辞，模板已经能完成功能，因此它是可选增强，不应成为主流程成功条件。`EvaluationJudgeAgent` 只作为补充观察，不替代固定答案和确定性断言。

不增加工具调用 Agent、RiskAgent、RankingAgent 或 PlanComposerAgent。当前场景没有需要模型自主选择工具的真实变化点，增加这些角色只会放大延迟、成本和调试难度。

## 两级完成门槛

### 面试可演示门槛

31-32 号完成后必须能够在无真实 API key 的固定夹具模式和有 API key 的真实模式下展示：

1. 饮食、健身、作息请求被识别并路由到不同领域模块；
2. 信息不足时进入结构化澄清，回答后继续原会话；
3. 响应只引用输入候选，候选越界会被拒绝并降级；
4. API key 缺失、超时或非法 JSON 时返回可用模板，不产生 500；
5. Trace 能解释每一步状态、Agent 调用、校验和降级原因。

这个门槛代表“Agent 主流程已经成立”，但不等于完整健康 MVP。

### 完整 MVP 门槛

31-36 号全部完成后，再要求小型正式资源集、餐食 hybrid RAG、健康档案、可持久化周计划、三阶段风险规则、用户页面和部署证据。每个阶段在自己的票据内完成测试，36 号只负责汇总和从干净环境复现。

## 最小数据规模

- Agent 垂直闭环：允许使用版本化种子资源，不等待外部 ETL；至少覆盖餐食、动作和作息各自的成功、空结果和风险场景。
- 完整 MVP：导入经过审核的小型子集即可，建议 100-300 条餐食、20-40 个 `plan_ready` 动作和 10-20 条作息事实；数量不是验收标准。
- 没有明确再分发许可的媒体使用稳定无图状态。图片不是推荐逻辑成立的前置条件。
- 全量 1,000 条餐食候选、1,324 个动作和媒体完善属于后续扩量，不阻塞首版。

## 面试讲解主线

建议按“问题、取舍、证据”讲，而不是按 Agent 数量讲：

1. 问题：自由 LLM 输出不可控。取舍：Agent 只做语义理解和表达，Java 掌握资源、数值、风险和状态。证据：候选越界与非法 JSON 自动降级。
2. 问题：外部模型不稳定且难测试。取舍：Agent 运行接口隔离 AgentScope，固定夹具适配器复现所有主流程。证据：无 API key 仍能完成测试和演示。
3. 问题：RAG 不能覆盖硬约束。取舍：先结构化过滤，再语义召回，再确定性排序。证据：硬约束命中率 100%，并记录 structured-only/hybrid 对比。
4. 问题：健康计划不能由模型自由生成。取舍：确定性组合、版本快照和三阶段 Guard，Agent 只解释。证据：未经校验的计划无法保存或激活。

## 剩余风险

- 31 号目前只有未提交、未运行验收的本地代码草稿，不能视为完成；后续开发应先审查这批草稿，再决定采用或调整。
- 当前仓库没有测试目录。32 号必须建立最小自动化测试基线，不能把所有测试推迟到 36 号。
- 真实 DashScope 输出仍可能受模型版本影响。固定夹具保证回归，少量真实模型冒烟保证集成，两者不能互相替代。
- 完整 31-36 号范围仍明显大于一个普通课程 Demo；时间不足时应优先保证 31-32 的 Agent 主流程和 34 的最小周计划，不以资源数量和页面数量换取表面完整度。
