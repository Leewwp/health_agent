# 面试演示主流程修复规格：餐食召回、计划说明与连续对话

Status: resolved (2026-08-30；方案 A 实施完成，全量/MySQL 门控/前端测试与真实浏览器验收通过)

## Problem Statement

2026-08-30 的真实验收发现，当前健康 agent 的绝大多数聊天、简报、计划生命周期、资源浏览和移动端流程可以运行，但面试演示最核心的“带偏好的餐食推荐”存在确定性可复现的失败路径：在当前审核数据库和启动方式下，新会话输入“推荐清淡的晚餐”会返回 HTTP 200，却没有推荐卡、没有推荐前预检，也没有“开始推荐”操作。旧 `/api/v1/diet/**` 链路对同一输入仍能返回餐食，造成两个入口行为分叉。

根因是结构化餐食检索器只将 `mealTime` 传给审核餐食 Reader，数据库查询虽然支持 `mood`、`scene`、`healthGoal`、`cuisine`、`foodType`、`taste`、`convenience` 等八个餐食槽位，实际调用时其余条件均为空；随后领域模块才在固定的 50 条召回窗口中做严格过滤。查询只按 `updated_at DESC` 排序，没有稳定的次排序键。当满足条件的餐食不在前 50 条时，严格过滤得到零候选。当前数据库有清淡且适用于晚餐/三餐的 APPROVED 公共餐食，但它们可能被窗口截断。

同一会话中还存在两个影响演示可信度的次要问题：

- 同领域换餐次时，历史非空偏好会继续被合并；例如先输入“清淡晚餐”，再输入“中午吃什么”，`healthGoal=清淡` 仍可能保留。跨领域切换已有投影和暂停语义，这不是跨域隔离失效，而是同领域新请求缺少明确的替换/reset 语义。
- 训练计划唯一候选复用时，后端会生成“候选不足，按指定训练日复用”的 `explanation`，但计划页只渲染结构化 `generationNotes`，用户看不到该说明。后端测试通过不能证明面试演示中的用户可见性。

整周餐食回退可能导致生成后的草稿因每日能量越界而无法启用，这是当前严格校验契约的已知边界，不应被误报为激活实现错误；但若演示脚本要求“生成后立即启用”，需要显式处理或提前提示。

## Solution

修复以健康聊天 API 和 `HealthOrchestratorService` 的外部行为为最高验收边界，确保面试演示中的主流程可复现、可解释、可回归：

1. 修复审核餐食的结构化候选完整性。所有实际参与严格匹配的显式餐食槽位必须能够影响 Reader 召回；召回排序必须在 `updated_at` 之后追加稳定的唯一键排序。实现必须继续遵守方案 B 的读取边界，不能让检索器直接依赖 Mapper。
2. 保留餐食混合召回的硬约束和语义召回职责。实现者必须评估“全槽位 SQL 硬召回”和“较宽确定性召回池 + 领域严格过滤/二次查询”对 Hybrid 的影响，选择能保证条件完整性且不让向量结果绕过硬约束的方案，并同步更新接口注释、测试和 ADR 相关说明。
3. 在同域连续对话中提供可解释的换主题行为。默认继续支持活动简报/推荐上下文的短答继承；只有明确的“换成/改为/重置条件/只看某餐次”等表达才替换或清除对应槽位，不得因为修复本问题而破坏跨域暂停/恢复和综合计划共享目标继承。
4. 让训练候选稀缺说明成为用户可见的计划生成说明，并与已有 `generationNotes`、计划详情、版本详情和旧 metadata 兼容策略保持一致。
5. 对能量回退和训练补充项文案做低风险改进：能量越界应在生成后、启用前清晰可见；训练补充项、摘要和前端公共标签使用统一用户词语。除非验收脚本明确要求一键启用，不改变现有 WARNING 阻断规则。

## User Stories

1. As a 健康聊天用户, I want 输入“推荐清淡的晚餐”后看到可用餐食候选, so that 面试演示的最高频主流程不会以空结果结束。
2. As a 健康聊天用户, I want 餐次和健康目标同时参与审核餐食候选召回, so that 严格过滤不会因为前 50 条窗口遗漏而误报无候选。
3. As a 健康聊天用户, I want 菜系、餐食类型、口味、便利性等已声明槽位被一致消费, so that 浏览页和 Agent 推荐对同一词表有相同含义。
4. As a 健康聊天用户, I want 相同数据快照下相同输入得到稳定候选顺序, so that 验收记录不会因数据库执行计划变化而失效。
5. As a 健康聊天用户, I want 推荐前预检在候选非空时稳定出现, so that 我可以看到已确认条件并选择“开始推荐”或“补充”。
6. As a 健康聊天用户, I want 推荐卡只来自 APPROVED、PUBLIC 且满足全部硬约束的餐食, so that 扩大召回池不会绕过审核、过敏原或排除 ID 规则。
7. As a 健康聊天用户, I want 向量召回和结构化召回最终使用同一套硬约束, so that 语义相似度不会把不满足餐次或偏好的餐食带入结果。
8. As a 旧饮食链路用户, I want `/api/v1/diet/**` 继续工作并保留 `foodType` 兼容字段, so that 健康链修复不会回归旧入口。
9. As a 健康聊天用户, I want 同一会话从“清淡晚餐”改问“中午吃什么”时能够明确替换旧条件, so that 新主题不会被旧偏好悄悄卡住。
10. As a 健康聊天用户, I want 没有明确替换语义时仍能继承当前简报上下文, so that 澄清短答不需要重复所有条件。
11. As a 健康聊天用户, I want 跨到作息或健身后旧餐食简报暂停而不丢失, so that “回到餐食计划”仍能恢复原进度。
12. As a 综合计划用户, I want 餐食和训练共享目标的继承行为保持不变, so that 修复同域餐食推荐不会污染综合简报。
13. As a 训练计划用户, I want 唯一动作被多个训练日复用时看到候选不足说明, so that 重复安排是可解释的确定性降级而不是静默行为。
14. As a 训练计划用户, I want 候选不足说明出现在计划页和计划详情中, so that 不需要查看数据库或 Trace 才能理解结果。
15. As a 训练计划用户, I want 版本详情中的候选不足说明与当前计划快照一致, so that 历史版本仍可审计。
16. As a 计划用户, I want 餐食整天回退时看到未满足偏好和能量风险, so that 我知道为什么草稿可能不能直接启用。
17. As a 计划用户, I want WARNING 阻断规则继续保护能量和风险约束, so that 修复推荐流程不会放松安全校验。
18. As a 聊天用户, I want 训练补充项使用稳定的中文标签, so that “器材/器械”“训练日/训练日期”不会在同一张卡片中漂移。
19. As a 维护者, I want 代码注释、Reader 契约和规格都明确八个餐食槽位, so that `foodType` 不会再次被遗漏。
20. As a 维护者, I want 失败路径记录检索模式、候选数量和降级原因, so that Trace 能证明是召回、严格过滤还是向量服务导致空结果。
21. As a 维护者, I want 新增回归用例在真实 MySQL 和普通单元测试中同时覆盖, so that 本地 seed、CI 数据库和线上迁移不会产生不同结论。
22. As a 面试演示准备者, I want 一份可重置、可重复运行的验收脚本, so that 修复后的浏览器证据可以替换过期的 2026-08-29 记录。

## Implementation Decisions

- 主行为边界是健康聊天 HTTP API；编排器仍负责意图、槽位合并、检索、推荐前预检、响应和会话持久化。不得新建平行的推荐状态机。
- 餐食领域使用完整八槽位定义：`mealTime`、`mood`、`scene`、`healthGoal`、`cuisine`、`foodType`、`taste`、`convenience`。所有新增注释、接口说明、测试命名和规格用“八个餐食槽位”，不得继续使用“七维”这一过时说法。
- Reader 仍是审核餐食数据库的唯一读取边界；检索器、Hybrid、MealModule 和编排器只消费 Reader 接口及 `ReviewedMeal`。不允许把 MealMapper 依赖扩散到调用方。
- 结构化召回必须满足以下外部不变量：显式槽位不会在召回入口被静默丢弃；同维度多值保持 OR、跨维度保持 AND；餐次“早餐/午餐/晚餐”继续兼容资源标签“三餐”；返回只包含 APPROVED + PUBLIC；排序在主排序字段相同的时候仍然稳定。
- 上一轮 `meal-facet-hardening` 的已闭环合同是本规格的回归前置条件：canonical facet 文件、13 个 cuisine/11 个 foodType 词表及其顺序/hash 不变；295 条 seed 餐食的 facet 非空、词表内、无单字碎片；复合稳定来源键和 `facetSource` provenance 不变；fresh-schema/legacy V1–V24 投影收敛不变；已应用迁移不可修改；ETL 重新运行仍然幂等。
- 共享词表只定义“可识别/可筛选的值”，不要求健康链和旧 diet 链返回完全相同的排序或逐 ID 候选。修复健康链召回时不得通过扩大词表、把“中餐”加入支持集合、重写演示分类或修改 seed 来掩盖召回问题。
- `foodType` 必须贯穿结构化 SQL、领域严格过滤、Hybrid 向量回查、计划偏好过滤、旧链 request/response 转换和浏览/count；不能出现“浏览可筛选但 Agent 只把它当排序文本”的半实现。`MealRankService` 当前未把 `foodType` 纳入分数时，必须明确这是硬过滤字段还是补齐排序维度，并增加回归说明，不能静默改变分数含义。
- “三餐”兼容是共享行为合同：早餐、午餐、晚餐查询都必须命中带“三餐”的资源；此规则要同时覆盖结构化 SQL 和 Hybrid `matchesSlots` 最终校验，不能因增加全槽位召回而让向量命中路径表现不同。
- 实现者应优先比较两种方案并记录选择理由：
  - 方案 A：将当前查询中所有合法、非空的餐食槽位传给 Reader 的结构化 SQL，并以 `updated_at` 加稳定 ID 排序。
  - 方案 B：保留较宽的结构化池以支持 Hybrid 语义排序，但通过确定性分页/扩大池/按条件二次召回保证严格过滤所需的候选完整性。
  方案选择不能只依据单元测试；必须验证结构化降级、Hybrid 有向量命中、向量无命中和过敏原/排除 ID 场景。无论选择哪一方案，不能让向量结果绕过全部显式硬约束。
- 修改结构化召回语义时必须同步更新 ReviewedMealReader 注释、StructuredMealRetriever 测试中“只传餐次”的旧断言、Hybrid 候选池说明和相关 ADR/规格。保留现有 `MealModule.matchesStrict()` 作为领域级最终防线，不以删除严格过滤换取候选数量。
- 修改结构化召回语义时必须同步更新 ReviewedMealReader 注释、StructuredMealRetriever 测试中“只传餐次”的旧断言、Hybrid 候选池说明和相关 ADR/规格。保留现有 `MealModule.matchesStrict()` 作为领域级最终防线，不以删除严格过滤换取候选数量。旧测试不能简单删除；必须替换为“完整槽位被消费且严格过滤仍生效”的行为断言。
- 不新增数据库表或 Flyway 迁移，不修改 V1–V24 已应用迁移，不重生成或覆盖 `current-corpus-v2` 的历史版本，除非实现者证明现有排序或候选索引无法满足稳定性并先记录影响。P0 首选改调用参数、排序和候选窗口策略。
- 不修改 `reviewed_resources.sql`、`data/meal/facets.json`、`manual_meals.json`、facet manifest、ETL 稳定键算法或 seed provenance 来修复推荐空结果。若测试需要数据，使用隔离的 MySQL 测试行/临时 cohort，并在测试结束清理。
- 任何候选池扩大都必须证明不会改变上一轮的审核边界：仍只读 APPROVED + PUBLIC，仍执行过敏原、排除 ID、全部显式槽位和“三餐”兼容；不得用 `LIMIT` 放宽或让 PENDING/个人餐食填充窗口。
- 同域槽位替换采用显式语义：普通澄清短答继续合并；“换成/改为/重置条件/只看”等表达可替换或清除对应槽位。跨领域时继续使用当前实现的 `activeSlots` 投影和简报暂停/恢复，不得清空另一侧简报。
- 候选稀缺说明优先进入已有生成说明领域模型，使计划列表、详情 API、版本详情和前端只消费一个结构化来源。若选择直接渲染现有 `PlanView.explanation`，必须确认列表/详情/版本快照的兼容性，并避免把后端自由文案拆成多个不一致字段。
- 旧计划 metadata 缺失时保持非空空集合；新字段不能破坏旧版本反序列化。所有用户可见说明必须经过现有 HTML 转义和移动端布局约束。
- 能量回退继续保留严格 `ENERGY_OUT_OF_RANGE` WARNING 和启用前校验。若生成器增加能量可行性约束，必须证明不会改变“整天回退、仍保留餐次/唯一性/多样性约束”的既有合同；否则只增加生成后提示，不放宽启用 Guard。
- 训练补充项、训练简报摘要和前端公共槽位标签统一为当前产品词语；先做术语一致性和行为测试，不为跨 Java/JavaScript 共享词表引入新的构建系统或复杂代码生成机制。
- 所有代码注释和用户提示继续使用中文；不记录真实 API key、完整 prompt 或敏感匿名用户数据。

## Testing Decisions

- 测试最高接缝是健康聊天 API/`HealthOrchestratorService`，优先断言外部响应字段和状态，而不是私有 helper 或 SQL 字符串。必须覆盖：新会话带偏好推荐前预检、确认后卡片、空候选降级、同域换主题、跨域暂停/恢复、旧链路兼容。
- `StructuredMealRetriever` 单元测试应证明：完整槽位被传递或被所选候选策略消费；严格过滤仍执行；过敏原和排除 ID 在排序前生效；同分候选顺序稳定。不得继续把“只使用餐次”作为不可变产品合同，除非实现者选择方案 B 并提供完整性证明。
- `DbReviewedMealReader`/真实 MySQL 测试应构造满足条件的记录位于初始排序窗口之外的场景，验证“餐次 + 清淡”仍能返回；同时验证八槽位 AND/OR、三餐兼容、APPROVED/PUBLIC 边界和稳定排序。测试应使用真实 Reader seam，不直接断言 Mapper 内部实现细节。
- `DbReviewedMealReader`/真实 MySQL 测试应构造满足条件的记录位于初始排序窗口之外的场景，验证“餐次 + 清淡”仍能返回；同时验证八槽位 AND/OR、三餐兼容、APPROVED/PUBLIC 边界和稳定排序。测试应使用真实 Reader seam，不直接断言 Mapper 内部实现细节。测试数据不得修改发布 seed 或 facet manifest。
- Hybrid 测试应覆盖结构化候选、向量候选、两者交集、向量无命中降级、向量命中但硬约束不满足被丢弃，以及向量命中“三餐”资源时早餐/午餐/晚餐兼容。结果必须不因扩大结构化池而绕过 `matchesSlots`、过敏原、排除 ID、foodType 或任一其他显式槽位。
- `meal-facet-hardening` 回归套件必须继续通过：canonical vocabulary drift、seed row-level facet invariants、fresh-schema V1–V24 projection comparison、merged browse/count SQL、旧 `/api/v1/diet/**`、foodType 未支持通道、ETL 幂等与版本/hash 校验。任何失败都视为本规格未完成，不得通过删测试、放宽断言或更新基线数字解决。
- 增加一个“共享 facet 不变性”验收：修复前后对同一数据库快照执行浏览 API 与审核 Reader，所有资源的 `cuisine`/`foodType`/`mealTime` 标签、`facetSource`、source key 映射和 APPROVED/PUBLIC 数量保持一致；允许候选排序变化，但不允许标签投影变化。
- 训练计划测试应保留唯一候选按全部指定训练日复用、零候选不放宽、Agent/规则 fallback 共用候选白名单，并新增“计划详情或结构化生成说明可见”的断言。后端只断言字符串存在不足以完成本规格。
- 前端 Node 行为测试应覆盖：计划页渲染候选不足说明、旧空 metadata 不报错、长说明转义、移动端不产生横向溢出；训练补充项标签在澄清卡和可补充 chip 中一致。
- 运行验证顺序：先执行针对性 Maven 单测和前端 Node 测试，再执行 `mvn test`，有 MySQL 时执行 `mvn test -Ditest.mysql=true`。Qdrant/live-model 仍按仓库既有独立门控，不得把跳过门控当成通过。
- 修复后必须用真实浏览器通过同源入口重跑“推荐清淡的晚餐”“中午吃什么”“训练唯一候选复用”“生成后查看说明”“同域换主题”和移动端 390×844；记录 URL、视口、输入、响应关键字段、候选数量和截图路径。旧的 2026-08-29 清淡推荐证据在复验前视为过期。
- 验收必须同时检查 Trace 与数据库：Trace 能区分结构化空召回、严格过滤后为空、向量不可用和正常预检；数据库只验证测试产生的数据，不把当前匿名演示用户的历史记录作为固定基线。

## Out of Scope

- 不重写健康 agent 的总体状态机、意图路由、简报生命周期或方案 B 资源读取边界。
- 不回退或重做 `meal-facet-hardening`：不改变 canonical 词表、seed 数据、ETL 稳定键、facet provenance、V24 纠正迁移、fresh/legacy 收敛、browse/count 合并 SQL、foodType 未支持通道或旧 diet 兼容。
- 不把所有历史槽位无条件清空；活动上下文继承、跨域暂停/恢复和综合计划共享目标继承仍然有效。
- 不要求健康链和旧 diet 链返回逐 ID 完全相同的候选集合；验收共同硬约束、共享词表、非空结果和可解释行为。两条链路允许使用不同的排序和语义能力。
- 不让普通 fixture 推荐自动变成审核数据库的八槽位过滤，除非另有规格明确修改 fixture 合同。
- 不扩充餐食或动作数据集，不把“候选不足”修复为静默放宽部位、器械、难度、过敏原或风险约束。
- 不在本规格内建设长期偏好学习、Agent 增量编辑已启用计划、作息指南 RAG、生产级账号体系或新的后台管理功能。
- 不因为一次运行态观察就修改种子数据、统一刷新所有 `updated_at` 或新增无必要的迁移。
- 不把“健康链与旧链逐 ID 相同”设为硬要求，也不为追求 ID 一致而破坏健康链 Hybrid/结构化路径；共享的是 facet 词表、硬约束和可解释非空行为。
- 不把能量 WARNING 改成允许危险计划启用；若要让所有回退计划都可直接启用，需另立规格并重新定义计划可行性算法。
- 不以跨语言共享词表生成器、前端框架迁移或大规模 UI 重构解决少量文案不一致。

### 当前已确认的实现证据

- 当前 `POST /api/v1/health/chat` 对“推荐清淡的晚餐”返回 200，但无 `displayBlocks`；对仅餐次输入可以进入推荐前预检。
- 当前 MySQL 有 295 条 APPROVED 公共餐食，存在清淡且晚餐/三餐兼容的记录；晚餐结构化排序窗口可能不包含这些记录。
- `MealMapper.search` 已有八槽位 JSON 谓词；缺陷不是数据库缺列，而是调用参数和候选窗口策略。
- `TrainingPlanGenerationService` 已产生候选稀缺 explanation；缺陷是计划页未展示。
- `MealPlanPicker` 的整天偏好回退和 `PlanValidationService` 的能量 WARNING 都是现有设计行为；不要把它们与 P0 召回错误混为一谈。

### 上一轮修复的回退风险清单

- **数据/版本回退**：改动推荐 SQL 或启动流程时误触 seed ODKU、`updated_at`、facetSource 或稳定来源键，导致 fresh/legacy 投影再次分叉。防护：本规格禁止修改发布 seed/manifest，必须重跑上一轮静态和 fresh-schema 套件。
- **字段回退**：只修 `healthGoal`/`cuisine` 而遗漏 `foodType`，或把 `foodType` 只用于浏览不用于 Reader/Hybrid/计划。防护：八槽位矩阵和 `foodType` 未支持通道回归。
- **检索边界回退**：扩大窗口时让 PENDING、个人餐食、过敏原资源或被排除资源进入结果。防护：Reader APPROVED + PUBLIC、领域硬约束、Hybrid 二次回查三层断言。
- **三餐语义回退**：结构化 SQL 命中“三餐”，但向量回查只做精确字符串比较而丢失早餐/午餐/晚餐兼容。防护：三种餐次在两条召回路径各测一次。
- **排序/评分回退**：为稳定排序改变浏览页 id 升序、旧链排序或 MealRankService 分数定义。防护：区分 Reader 召回排序、领域重排排序和浏览分页排序，分别断言；不要把 `id DESC` 传播到 browse API。
- **测试契约回退**：删除“只传餐次”测试而没有补等价外部行为测试，造成下一次漏传槽位无人发现。防护：替换而非删除，并要求 API、MySQL、Hybrid 三层覆盖。
- **版本证据回退**：重新生成 corpus/embedding/evaluation 报告但未绑定同一 resourceVersion。防护：本任务不重建数据索引；若候选策略影响索引输入，必须显式升级版本并重跑对应报告。

### 完成定义

本规格只有在以下条件全部满足时才算完成：

1. “推荐清淡的晚餐”在真实审核数据库环境中进入推荐前预检，并在确认后返回至少一张满足硬约束的餐食卡；重复运行候选顺序稳定。
2. 健康链与旧链路对同一输入都能产生可解释的非空结果，但不要求逐 ID 相同。
3. 结构化、Hybrid、向量不可用降级和严格过滤回归全绿，且不违反 Reader 边界。
4. 训练唯一候选复用说明在计划 API 和面试演示计划页可见。
5. 同域换主题有明确替换/reset 语义，既有澄清继承、跨域暂停/恢复和综合计划行为不回归。
6. 能量 WARNING、旧计划 metadata 兼容、旧 diet 链、移动端无横向溢出和中文标签测试通过。
7. 真实浏览器证据更新，过期的 2026-08-29 清淡推荐记录不再作为当前通过依据。
8. `meal-facet-hardening` 的静态校验、fresh-schema、Reader/Controller、旧 diet、foodType、ETL 和版本/hash 回归全部保持通过，且没有通过修改 seed、迁移历史或放宽断言来“修复”P0。
