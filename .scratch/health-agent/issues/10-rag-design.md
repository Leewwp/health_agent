# 10 RAG 技术选型与落点设计

- Type: grilling
- Status: resolved
- Blocked by: 09

## Question

**RAG 如何引入**（用户 2026-08-09 补充要求："根据用户需求找到可靠的信源"，技术选型待探讨）？前序会话已给出两个落点方向（见 `docs/research/frontend-backend-split.md` 与交接文档 §4.2）：

1. **候选召回层**：`meal_item` 文本向量化（菜名+描述+标签 → DashScope text-embedding），用户 query 嵌入后**语义召回 + 结构化过滤（hybrid）**，再进现有 LLM 重排（MealRankService 已存在）。只插一层，orchestrator 零改动。
2. **范围边界**：本票设计餐食候选的混合检索，并评估受控的训练/作息指南证据检索。用户历史反馈由 17 号“类型化资源与偏好闭环”设计，属于偏好记忆与重排，不再混称为 RAG。

技术选型待决：
- **推荐基线**：导入阶段离线生成并持久化餐食 embedding，启动/刷新时加载归一化向量到进程内索引；MVP 规模使用 Java 暴力余弦即可。MySQL 是持久化源，不在每次请求中扫描 JSON/BLOB 计算向量。
- **技术 seam**：定义小型 `EmbeddingClient` 与 `MealRetriever` 接口，生产 adapter 调 DashScope embedding，测试 adapter 使用固定向量。项目已经使用 AgentScope，不为一个 embedding 调用额外引入整套 Spring AI；只有确认其兼容性和收益后才重开该选择。
- 嵌入模型：DashScope text-embedding 的型号选择、离线/降级策略（api-key 未配置时系统现状为降级可用——RAG 层同样需兜底）。
- **已确认**：作息事实表（08）走结构化条件检索并返回来源引用，不向量化；指南证据检索只检索已核验来源段落，不参与数值和风险决策。
- hybrid 策略：过敏、来源、餐次等硬约束先过滤；结构化标签分与语义分归一合并，再进现有重排。embedding/API 失败时必须只走结构化检索，结果仍可用。
- 质量要求：离线标注查询集比较 structured-only 与 hybrid 的 Recall@K；如果没有可复现提升，不把 RAG 写成已完成卖点。

技能：/grilling。解决会话如需补查（Spring AI MySQL VectorStore 现状、DashScope embedding 接口）可先派 /research 子代理。

阻塞说明：向量化哪些 meal_item 字段、营养和份量约束如何过滤，取决于 09 号（meal_item 表结构改造）的最终 schema。

## Answer

2026-08-10 已决策：第一版只实现餐食候选召回 RAG；训练和作息指南检索移出首版范围。RAG 不让 LLM 自行决定营养、风险或训练剂量。

- 离线为餐食名称、描述、食材和已审核标签生成 embedding，运行时使用结构化条件过滤与语义召回合并候选。
- 过敏、餐次、硬性饮食限制和来源状态等先由确定性规则过滤；语义分和结构化标签分再归一化合并，最后交给现有排序/解释链路。
- 通过 `EmbeddingClient` 和 `MealRetriever` 隔离模型供应商；MVP 使用进程内归一化向量和 Java 暴力余弦，不引入无真实缺口的向量数据库或完整 Spring AI 栈。
- Embedding 服务不可用、API key 缺失或超时时只走结构化检索，推荐功能仍可用。
- 作息事实表本身、健康档案、用户偏好、训练动作计划资格和营养计算不使用 RAG；它们分别使用结构化事实查询、档案读取、偏好重排、动作元数据过滤和确定性公式。
- 使用标注查询集比较 structured-only 与 hybrid 的 Recall@K、硬约束命中率和降级正确率；没有可复现提升时不把 RAG 作为已完成卖点。

## 后续场景：训练和作息指南证据检索

该场景不属于首版。后续如需要，可从已核验的训练和作息权威来源建立小型、版本化知识库，按品类、主题、适用人群、来源机构和发布日期检索相关段落，并在回答中返回引用。

可行性较高，原因是现有项目已经有来源研究、AgentScope 调用链和 RAG 的 `EmbeddingClient` 抽象；新增的主要工作是文档清洗、切块、元数据、引用 DTO、指南检索器和评估集，而不是重做编排层。

估算工作量：

- 受控 MVP（10～20 篇已核验文档或研究摘要、离线切块、复用餐食向量索引方式）：约 4～7 个开发日。
- 若加入 PDF/OCR、动态网页抓取、多语言来源、自动更新和大规模来源治理：约 1～2 周以上，不建议放入当前首版。

范围限制：不开放任意网页实时检索，不接收用户医疗文档，不让检索结果直接生成训练处方或医疗结论；训练计划的剂量、风险和动作资格仍由确定性规则和人工审核白名单决定。
