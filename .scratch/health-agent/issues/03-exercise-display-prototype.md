# 03 健身动作展示原型

- Type: prototype
- Status: resolved
- Blocked by: —

## Question

健身动作在页面中**如何展示**（Q5 遗留的"再确认健身动作在页面中的展示方式"）？用 /prototype 技能做一个可交互的静态 HTML 原型，验证三个交互面：

1. **动作浏览页**：卡片网格（GIF 缩略图 + 名称 + 部位/器材标签）+ 筛选器（部位/器材/训练目标）+ 分页或滚动加载——数据集的 1,324 动作全量可筛。
2. **对话内详情抽屉**：agent 在消息中推荐动作时，详情抽屉展示什么（名称、GIF、中文步骤、肌群、器材）、如何唤起、与消息气泡的布局关系。
3. **"喜欢/收藏"入口**：浏览页与详情抽屉里的收藏/喜欢按钮放在哪、收藏状态如何呈现。

原型还必须验证：媒体加载失败时的稳定布局、Gym visual 署名位置、全量浏览动作与“可进入计划的审核动作”如何区分，以及用户从计划页局部替换动作时是否复用同一详情交互。原型只决定交互，不决定前端框架和模块拆分；后者由已解决的 07 与 18 号票承接。

已确认事实：1,324 动作、每条含 GIF + 180×180 缩略图（远端 URL，需保留 Gym visual 署名）、10 部位 / 12 器材 / 目标肌群字段、中文步骤说明。展示密度与交互手感是本次验证重点（参照数据集自带的 index.html 浏览器做差异化）。

产出：可双击打开的原型文件，链接到本 ticket；原型结论（选择哪种展示形态、理由、对页面结构的影响）作为 Answer 记录。

## Answer

2026-08-10 已完成原型和真实浏览器验收，交互方向确认如下：

- 动作浏览页采用卡片网格、结构化筛选和分页或加载更多。
- 动作详情统一使用“详情抽屉（Detail Drawer）”，在动作浏览、对话推荐和计划局部替换中复用。
- 卡片和详情抽屉均提供收藏入口；计划入口使用“入门候选 / 可浏览、可收藏”区分计划资格与用户偏好。
- 媒体使用固定尺寸区域，GIF 或缩略图加载失败时显示稳定占位内容。
- Gym visual 署名同时出现在动作详情和页面底部。

原型文件位于 `src/main/resources/static/prototypes/exercise-display-prototype.html`，已在提交 `cf62449` 的独立 worktree 中完成。

### 原型结论

1. 浏览页使用左侧部位/器材/目标筛选和紧凑卡片网格，收藏作为用户入口；计划资格只在计划入口和详情层解释。
2. 对话推荐使用候选动作卡片，点击后打开统一详情抽屉，展示 GIF、中文步骤、目标肌群、器材和计划资格。
3. 原型曾探索“日期容器 → 当日内容块 → 训练动作套组”和动作池交互；正式 MVP 只复用日期容器、内容块和详情交互，不实现调参数、移除、拖入或资源替换。

### 浏览器验收

- 桌面视口 `1710×983`：A 变体筛选后显示 7 条入门候选，关键词“硬拉”显示 1 条；B 变体有 2 条对话推荐和详情抽屉；C 变体有 3 天、3 个训练套组和 7 个入门候选。
- 详情抽屉包含动作信息、中文步骤、收藏入口和计划资格说明；收藏状态可在页面内切换并显示反馈。
- 故意失效媒体保留固定比例展示位、失败占位、文字信息和 `© Gym visual` 署名。
- 计划套组支持参数调整、移除动作，以及将候选动作拖入折叠套组后自动展开；拖拽成功后套组总时长和动作数量更新。
- 移动视口 `390×844`：浏览页和计划页无横向溢出，计划操作控件保持在视口内；详情抽屉在动画稳定后宽度与视口一致。

### 实施阶段待定事项

1. 移动端详情抽屉是否保持全屏宽度，还是改为底部半屏抽屉。
2. 浏览页首屏采用分页还是滚动加载。
3. 收藏何时写入后端偏好事件，以及计划资格的最终用户文案。
4. 本原型只决定交互参考，不直接决定前端模块拆分；生产前端仍由 18 号票承接。
