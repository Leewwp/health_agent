# 12 用户身份与数据隔离方案

- Type: grilling
- Status: resolved
- Blocked by: 11

## Question

在最终部署拓扑明确后，系统采用哪一种用户形态与身份机制？必须消除浏览器任意修改 `X-User-Id` 后读取其他用户会话、偏好和计划的风险。

待决策：

1. 产品形态是可重置的匿名演示、单演示账号，还是可长期保存数据的真实多用户系统。
2. 同源部署时是否采用 Spring Security Session + BCrypt；前后端跨域时如何处理 cookie、CORS、CSRF 与会话存储。
3. 匿名标识、用户档案、计划和偏好的数据保留/清理规则。
4. 管理端 Trace/评估页面如何与普通用户权限隔离。

约束：不为了展示技术默认引入 JWT；身份方案必须与部署拓扑、公开演示方式和 1-2 周预算一致。

## 研究输入与推荐

11 号调研已确认：Vercel 只托管静态前端，Spring Boot 后端部署在外部常驻环境。可选方案收敛为：

1. **匿名演示身份（推荐）**：首次访问由后端签发不可篡改的随机身份并放入 HttpOnly/Secure cookie；用户不注册，可在同一浏览器保存档案、偏好和计划，提供“重置演示数据”，服务端按 TTL 清理长期不活跃数据。前端不再发送可编辑的 `X-User-Id`。
2. **真实账号体系**：只有产品明确要求跨设备长期保存时，加入 Spring Security Session、用户名/密码、BCrypt、找回/重置和用户数据管理。成本和隐私责任明显增加。
3. **单一公共账号**：不推荐。并发访客会互相污染档案、会话、偏好和计划。
4. **JWT**：不推荐。同源或反向代理后的 Web 页面使用 session cookie 更简单；JWT 不解决用户注册、撤销、CSRF/XSS 和数据隔离本身。

若前端放 Vercel，优先评估把 `/api/**` external rewrite 到后端，使浏览器继续使用相对 API 路径并保持同源 cookie；若改用独立 API origin，则必须验收 CORS credentials、cookie SameSite/Secure、CSRF 和代理头。具体方式在 21 号部署票中确定。

## Answer

2026-08-10 已决策：第一版采用匿名演示身份，不开发真实账号体系，也不使用单一公共账号。

- 后端签发不可篡改的随机身份凭证，浏览器通过 HttpOnly Cookie 持有。
- 前端移除可编辑的 `X-User-Id`，会话、健康档案、计划和偏好均由服务端身份确定归属。
- 提供重置演示数据的能力，并按长期不活跃 TTL 清理匿名数据。
- 管理端 Trace 和评估接口与普通用户接口隔离并单独保护。
- 不为了展示技术引入 JWT；跨域部署时另行验收 Cookie、CORS、SameSite、Secure 和 CSRF 配置。
