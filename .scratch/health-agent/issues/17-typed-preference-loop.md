# 17 类型化资源与偏好闭环

- Type: grilling
- Status: resolved
- Blocked by: 03, 05, 09

## Question

餐食、动作和未来计划项如何使用无歧义的资源身份记录收藏、喜欢、不喜欢、采纳与对话明示偏好，并让这些事件真正影响下一次召回和重排？

当前 `recommend_feedback` 只有 `item_id`，加入动作后不同表可能出现相同 ID；“我喜欢俯卧撑”也不应被错误塞进训练部位槽位。

待决策：

1. `resource_type + resource_id`，或统一健康资源 ID 的取舍。
2. 收藏状态与推荐反馈事件是同一模型还是分离模型。
3. 浏览页行为、对话明示偏好和推荐后的采纳/拒绝如何归一化、聚合与衰减。
4. 哪些偏好作为硬过滤，哪些只参与重排；用户如何撤销和查看。
5. 反馈上下文的数量上限、隐私和无历史时的降级。

产出：事件模型、聚合偏好模型、接口、数据表和推荐模块消费规则。

## 首版确认

2026-08-10 已确认首版采用简化的类型化反馈：

- 使用 `resource_type + resource_id` 区分餐食、动作和计划项，不能继续只使用裸 `item_id`；
- 用户侧支持收藏、喜欢、不喜欢和采纳；
- 反馈事件进入后续候选过滤和重排，暂不实现复杂偏好衰减、高级画像和完整反馈历史管理；
- 无历史反馈时保持现有结构化排序和默认推荐，不依赖偏好数据才能工作；
- 动作浏览、对话推荐和计划页面共享资源身份与收藏状态。

页面交互由已完成的 03 号原型和后续 18 号前端信息架构承接；最终数据表和接口契约由 22、23 号票据收敛。

## Answer

2026-08-10 已按“满足项目需求的最小实现”确认：

- 资源身份使用 `resource_type + resource_id`。首版资源类型为 `MEAL` 和 `EXERCISE`；计划项引用底层餐食或动作资源，不单独建模为偏好资源类型。采纳计划项时，反馈仍指向底层资源，并保留计划上下文。
- 收藏、取消收藏、喜欢、不喜欢和采纳统一记录为类型化反馈事件。沿用并扩展现有 `recommend_feedback`，不新增独立画像表、事件总线或完整反馈管理页；当前收藏和偏好状态由最近事件计算。
- 现有意图 Agent 的结构化 JSON 新增 `preferenceSignals`，与 `slots` 并列。Agent 只负责理解用户的明示偏好；业务代码负责将名称解析为正式资源、校验资源类型并持久化。无法解析到正式资源的表达不写入偏好表，也不塞入训练部位等需求槽位。
- `DISLIKE` 对同一资源执行候选硬过滤；`LIKE`、`FAVORITE` 和 `ADOPT` 参与确定性重排。槽位、过敏和风险规则优先于偏好分。简单浏览不产生偏好事件；无历史反馈时沿用现有结构化排序和默认推荐。
- 收藏可以取消，不喜欢可以被后续喜欢覆盖；首版不提供独立偏好管理页。匿名用户推荐只读取最近 100 条反馈事件，匿名身份重置时一并清理偏好数据。

### 对实现的约束

1. 反馈请求和资源响应不得继续只传裸 `itemId`；旧饮食接口由兼容适配层补齐 `MEAL` 类型。
2. 偏好消费应位于候选过滤/排序层，不放入响应 Agent Prompt 中让模型自行决定过滤结果。
3. 任何偏好增强都不能覆盖硬约束、风险规则或候选资源资格；偏好数据不可用时必须确定性降级。
4. 18 号票只决定收藏入口、反馈控件和状态展示，不重新讨论资源身份与反馈语义。
