# 28 发布证据与验收门槛

- Type: grilling
- Status: resolved

## Question

冻结“可以交付”的证据矩阵：多品类意图/槽位/编排、健康档案量化、周计划不变量、风险规则、餐食 hybrid RAG、结构化作息事实、类型化反馈、旧饮食兼容、匿名隔离、降级和部署健康检查分别必须由哪些自动化测试、接口冒烟、真实浏览器场景或上线后检查证明？

需要给出固定夹具、Recall@K 与硬约束命中率的最低解释方式、媒体 404/空数据/慢网络、LLM/数据库/Redis/embedding 失败、移动端与桌面端验收范围，以及每个 M0-M4 的完成定义。没有这张矩阵，实施计划的“完成标准”仍无法复核。

## Answer

2026-08-10 已按“面试展示项目的最小实现”确认发布证据矩阵：

### 自动化核心

只自动化以下高价值逻辑：

1. 多品类意图、槽位和明示偏好解析；
2. `AgentInvoker` 两类适配器、Agent Schema/候选约束、编排路由与确定性降级；
3. Mifflin-St Jeor 量化目标和周计划不变量；
4. 三档风险规则；
5. 类型化反馈、旧饮食兼容和 requestId 幂等；
6. 餐食 hybrid RAG 的结构化过滤、Recall@K 对比和 Embedding 降级。

其他 Controller、页面和管理功能使用接口或浏览器冒烟，不追求所有 Java 类和页面分支的自动化覆盖。

### RAG 证据

使用固定的小型查询集记录 `Recall@3`、硬约束命中率、structured-only 与 hybrid 结果差异，以及 Embedding 失败回退是否正确。硬约束命中率必须为 100%；不设置牵强的绝对 Recall 门槛。如果 hybrid 没有可复现提升，就不把 RAG 写成项目成果。

### 浏览器证据

真实浏览器至少验收：

- 桌面端聊天 → 详情抽屉 → 收藏/反馈；
- 动作浏览 → 筛选 → 媒体失败 → 收藏；
- 周计划生成 → DRAFT 编辑 → 激活；
- `390×844` 移动端上述页面无横向溢出，详情抽屉和计划操作可用。

### 失败与部署冒烟

每类准备一个可复现样例：非法 JSON、未知枚举、候选越界、超时、API key 缺失、Embedding 不可用、候选为空、媒体 404、重复 `requestId`、Cookie 被篡改、未授权 admin 请求和 MySQL 不可用。Redis 只有在实际引入后才验收，不为尚未使用的组件增加测试。

### 里程碑门槛

- `M0`：Java 21 编译、环境变量和身份隔离通过；
- `M1`：固定夹具和真实 Agent 适配器、饮食/健身/作息路由、输出校验、确定性降级和 Trace 通过，达到面试可演示门槛；
- `M2`：审核资源子集、浏览 API、hybrid RAG 和结构化降级通过；
- `M3`：健康档案、周计划、校验和版本快照通过；
- `M4`：前端浏览器验收、旧 API 兼容、部署健康检查和干净环境复现通过，达到完整 MVP 门槛。
