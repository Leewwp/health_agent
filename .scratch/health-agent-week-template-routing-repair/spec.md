# 周模板、餐训适配与任务路由修复规格

Status: ready-for-agent

本规格承接 [ADR-0018](../../docs/adr/0018-week-template-training-priority-and-ambiguous-routing.md)，用于实施四个用户问题及其暴露出的通用误路由风险。ADR-0018、`CONTEXT.md` 和本规格共同构成执行合同；本文不重复已有历史规格的全文，只引用其边界并补充本轮实现所需的跨模块约束。

## Problem Statement

用户在健康 Agent 中遇到四类相互关联的问题：

1. 周计划对话要求提供或确认“目标周”，并出现“请给目标周的周一日期”等内部流程文案。用户只需要一个可参考、不会随现实时间过期的周模板，不需要计划与真实日历绑定。
2. 需求输入指引使用固定文本。用户已经填写菜系后，后续仍可能看到“还可以补充：菜系（如粤菜、川菜）”，导致系统状态与文案不一致。未支持偏好和已填写的受支持偏好也没有稳定、清晰的区分。
3. 综合计划将训练安排和固定餐食窗口直接合并，再由 Guard 把训练与餐食重叠判为硬错误。训练时间是用户主动设定的硬约束，餐食时间应当由系统适配；当前行为把可调度问题错误呈现为用户必须调整的冲突。
4. 已生成综合计划后，用户输入“训练时间改为下午五到六点”会被识别为 `ROUTINE + RECOMMEND`，开始回答训练时机或睡眠相关内容，而不是修改当前计划训练简报。当前“训练/运动 + 时间”作息启发式优先于计划上下文和字段修改解析，导致此前增加的“改为/调整为/改成”等关联词未能生效。

问题 4 还说明系统可能在其他输入上于不合理时机触发任务：快捷问题关键词、字段值、计划词和作息词的启发式存在边界重叠；Agent 输出虽经过枚举合法性校验，但尚未始终经过当前会话状态和任务生命周期的二次裁决。若继续堆叠例外关键词，会重现历史上的多份清单漂移和修一处坏一处。

## Solution

将本轮修复收敛为四个协同能力：不可过期的周模板、训练优先的餐训确定性调度、计划上下文优先的共享路由，以及规则无法唯一裁决时的受约束意图仲裁。保持现有 Spring Boot、MyBatis、健康会话、计划生命周期、资源读取边界和 vanilla ES Modules，不新增业务表或第二套健康状态机。

### 周模板与目标周

- `weekStart` 不再是训练简报或餐食简报的用户必填字段；缺失列表、追问、摘要和需求输入指引不得要求或展示“目标周”或具体周一日期。
- 三个生成入口（餐食、训练、综合）以及任何从聊天触发生成的编排路径，在生成边界统一派生“生成当天所在周的周一”作为内部锚点。训练-only、餐食-only、综合生成必须使用同一派生函数，不能各自计算。
- 旧会话 JSON 缺失内部锚点时按同一规则兼容读取；用户输入日期时不能静默覆盖、迁移或重新计算已经存在的内部锚点。
- 用户输入“改成 2026-09-07”“下周安排”等日期表达时，日期不进入简报、不改变计划语义、不触发周起始日一致性澄清。系统可以给出简短说明：计划按周一至周日作为参考，不需要指定日期。
- 对话中的简报摘要、确认/生成引导和普通回复隐藏内部日期；计划页保留周一至周日和具体项目日期的可视化，因为日期仍是编辑器和历史计划 API 的技术展示字段。
- 计划不根据当前日期、内部锚点或页面日期自动过期；生命周期仍由 `DRAFT/UNENABLED/ENABLED/HISTORY` 操作决定。
- `DraftPlanRequest`、生成服务和计划写入服务的缺省日期说明必须与上述派生规则一致。不能保留“缺省为下周一”的过时注释或实现。
- 保留现有数据库/API `weekStart` 和项目周范围字段，避免迁移破坏历史计划、版本快照、编辑器和列表接口；本轮不把字段从存储层删除。

### 训练优先的餐训时间适配

- 训练简报指定的训练日和时间窗口是硬约束；训练项目仍必须满足资源资格、风险、半小时粒度、周范围和不跨午夜等既有规则。
- 餐食项目保持餐次名称和默认时长：早餐 30 分钟、午餐 60 分钟、晚餐 60 分钟。默认起点继续为早餐 08:00、午餐 12:00、晚餐 18:00。
- 综合生成先得到训练项目，再将餐食项目送入确定性适配器。适配器优先尝试餐次默认时间；冲突时优先尝试训练结束后立即开始，允许餐食开始时间等于训练结束时间；训练后不额外增加 30 分钟间隔。
- 训练后无法放置时，尝试训练开始前倒推同等餐食时长。前后都无法放置时才返回稳定错误；不得让餐食与训练重叠，不得生成部分综合计划。
- 同一天多次训练按时间顺序逐一避让；调度必须基于已经放置的训练区间和同日已放置餐食区间，结果可重复且不能因遍历顺序随机变化。
- 餐食允许离开默认早餐/午餐/晚餐时间窗口，但当日可行边界固定为本地 `05:00-24:00`，餐食不得跨午夜。相邻区间使用 `[startTime,endTime)`，相邻合法。
- 自动适配成功不是 `SCHEDULE_OVERLAP`，也不能触发会误导用户“需要调整”的餐食窗口警告。Guard 仍保留最终重叠、粒度、跨午夜、周范围、资源资格和风险校验；需要通过适配标记或等价结构化事实区分“自动适配的窗口外餐食”和“用户/编辑器直接产生的窗口外餐食”。
- 生成说明、计划 metadata、版本快照可读取的生成说明和 Trace 均记录被移动的餐次、原始默认窗口、最终窗口、适配方向（训练前/训练后）以及无法适配时的稳定失败原因。
- 被移动的餐次与方向必须对用户可见：生成后的聊天回复和计划页生成说明分区至少一处展示适配结果（对应 US 22），不能只写入内部 metadata 与 Trace。
- 餐食-only 和训练-only 仍复用各自的默认生成行为；训练优先适配只在同一综合计划的餐食与训练集合需要共同占用时间轴时执行。
- 该时序替换 ADR-0014 的“先固定餐食、冲突即拒绝”生成规则，但不删除最终 Guard 或时间轴不变量。

### 计划上下文优先路由

- 路由共享判定必须先识别当前会话是否存在活动计划上下文、对应简报生命周期和可解释的字段修改，再决定是否把活动词 + 时间词视为作息切换。
- 在 `PLAN` 的餐食、训练或综合简报上下文中，出现“改为、调整为、改成、安排到、换成”等修改表达，且本轮文本可以被对应简报解析为字段更新时，优先留在计划上下文。
- “训练时间改为下午五到六点”“训练：调整为 17:00-18:00”“把训练安排到晚上七点”等必须更新训练时间字段并重新展示生成入口；综合上下文中只更新训练子简报，餐食子简报保持不变。
- 已生成或暂停的简报收到明确计划修改表达时，可以重新打开对应侧；普通字段短句在 `GENERATED/PAUSED` 状态不得无条件捕获。重新打开不直接改写已保存计划，用户仍需再次开始生成。
- “什么时候训练合适”“训练时段建议”“晚上几点后停止锻炼”“几点睡”等事实/建议问句保持 `ROUTINE` 处理；不能因存在训练词就把所有时间表达视为计划字段。
- 已有餐食计划上下文时，裸“餐食计划”无法区分新建与修改，必须澄清“修改当前餐食计划还是新建一份”，不能由模型猜测。
- 没有活动简报的新会话中，“把训练安排到晚上七点”等孤立修改表达仍按明确任务词进入对应域的 `PLAN` 创建侧（如 `EXERCISE + PLAN`），不因缺少上下文而退化为作息；存在已保存计划但没有活动简报时，修改表达进入“修改当前计划还是新建简报”的澄清，不猜测执行。
- `HealthBriefRouter`、意图修订服务和编排器必须共享同一结构化判定结果；不再在调用点增加第二套例外关键词。若路由器新增依赖，统一采用 Spring 注入或等价单一构造方式，消除生产实例与直接构造测试实例的行为差异。

### 确定性路由与歧义仲裁

- 确定性规则优先处理高置信输入：快捷问题及其同义表达、明确新建计划、明确修改当前计划、明确单次推荐、明确作息事实/建议。
- 快捷问题关键词只是候选入口，不是唯一自然语言入口；用户用同义、口语或完整句表达时，规则归一化仍应得到同一候选任务。
- 规则抽取应先保留所有可验证槽位和修改候选，再检测任务冲突、否定、转折、多时间从句、指代、当前计划引用和低置信度。
- 仅在存在多个任务候选、规则与会话状态冲突或无法唯一区分新建/修改/推荐/作息时，调用一次轻量意图仲裁 Agent。无歧义路径不调用模型。
- 仲裁 Agent 只返回受限的候选任务、领域、置信度和证据，例如 `NEW_PLAN`、`REVISE_PLAN`、`RECOMMEND`、`ROUTINE`、`CHAT`；不返回自由执行动作，不决定资源资格、风险结论或计划时间。
- Agent 结果必须经过领域/任务枚举校验、置信度阈值、当前会话计划生命周期、风险规则和资源约束复核。确定性的计划上下文和风险阻断不可被 Agent 覆盖。
- Agent 超时、非法 JSON、低置信度或与会话状态冲突时，保留规则已抽取的合法槽位并进入可理解澄清；不得猜测执行，不得随意回退到普通推荐。
- `HealthIntentAgentService` 的相关槽位选项准备、快路径和仲裁调用必须避免重复模型调用或递归调用；Trace 记录规则证据、Agent 是否调用、仲裁输出摘要、最终裁决和降级原因。

### 需求输入指引动态化

- 餐食、训练和综合简报的“还可以补充”文本统一由当前结构化简报计算，不再保留独立固定枚举字符串。
- 已填写且受支持的字段不再出现在可补充列表；全部可选项已填时不显示“还可以补充”。
- 未支持值（如餐食菜系“中餐”）保留在简报的未支持集合中，单独显示“已记录，暂不按它筛选”，并可继续提示当前受支持的菜系。未支持值不能被当作已满足的筛选字段，也不能导致用户输入整体丢弃。
- 未完整、解析失败和完整三类分支均必须使用同一动态列表计算；固定字段追问可以保留，但不得附带已经填写的可选项。
- 响应结构中的 `supplementable` 是前端渲染的唯一可补充项来源。前端不得再次从历史固定文案推断列表；旧响应缺少该字段时应采用空列表或明确兼容显示，不得恢复全量固定提示。

## User Stories

1. As a 周计划用户, I want 直接开始收集餐食或训练条件而不被要求提供目标周, so that 计划符合参考模板而不是日历任务。
2. As a 周计划用户, I want 对话摘要不显示内部日期, so that 我不会误以为计划会过期或必须在指定日期执行。
3. As a 周计划用户, I want 计划页仍显示周一到周日及具体安排, so that 我可以按一周网格查看和编辑项目。
4. As a 周计划用户, I want 系统在生成时自动建立不可见周锚点, so that 既保留现有编辑/历史 API 又不增加对话负担。
5. As a 周计划用户, I want 同一生成规则适用于餐食、训练和综合计划, so that 不同入口不会出现不同日期行为。
6. As a 周计划用户, I want 计划经过现实日期后仍可查看和使用, so that 参考模板不会自动失效。
7. As a 周计划用户, I want 输入“下周安排”或具体日期时不改变计划条件, so that 日期短语不会偷偷覆盖内部锚点。
8. As a 周计划用户, I want 日期输入得到简短易懂的说明, so that 我知道无需指定目标周而不被内部术语阻断。
9. As a 旧会话用户, I want 缺失内部锚点的历史会话仍可生成计划, so that 升级不会要求重新填写条件。
10. As a 餐食计划用户, I want 已填写菜系后不再看到菜系可补充提示, so that 指引与当前简报一致。
11. As a 餐食计划用户, I want 已填写餐食类型、口味和烹饪时长后相应提示消失, so that 我只看到真正还可以补充的字段。
12. As a 餐食计划用户, I want 可选项填满后不再看到“还可以补充”, so that 系统不会制造虚假的未完成感。
13. As a 餐食计划用户, I want 未支持的菜系被明确标记为已记录但暂不筛选, so that 我的偏好不丢失且能力边界透明。
14. As a 餐食计划用户, I want 未支持菜系存在时仍能看到受支持菜系选项, so that 我可以主动选择一个真正可筛选的替代条件。
15. As a 餐食计划用户, I want 未完整和解析失败时也看到动态可补充项, so that 指引不会因响应分支不同而恢复固定全文。
16. As a 综合计划用户, I want 训练时间与晚餐冲突时由系统自动调整晚餐, so that 我不必为了计划生成手动修改训练时间。
17. As a 综合计划用户, I want 训练结束后立即用餐, so that 调度不增加没有产品依据的等待间隔。
18. As a 综合计划用户, I want 餐食可以离开默认窗口但不跨午夜, so that 系统有足够空间避让训练又保持合理日期边界。
19. As a 综合计划用户, I want 相邻训练和餐食区间合法, so that 训练 18:00 结束、餐食 18:00 开始不会被错误判为重叠。
20. As a 综合计划用户, I want 同日多次训练按稳定顺序避让餐食, so that 每次生成结果都可复现。
21. As a 综合计划用户, I want 无法安排餐食时综合计划整体失败, so that 系统不会保存只有一半内容的计划。
22. As a 综合计划用户, I want 看到被移动的餐次和移动方向, so that 我理解最终时间为何不同于默认窗口。
23. As a 综合计划用户, I want 自动适配成功后不看到“时间冲突”或误导性窗口警告, so that 成功结果不会看起来像失败。
24. As a 计划用户, I want 在已生成计划后说“训练时间改为下午五到六点”, so that 当前训练简报被修改而不是触发作息推荐。
25. As a 综合计划用户, I want 训练侧修改只更新训练子简报, so that 餐食条件和偏好不会被清空或改写。
26. As a 计划用户, I want 修改后重新看到开始生成入口, so that 新条件经过服务端复核后才生成新草稿。
27. As a 计划用户, I want 生成态或暂停态的计划字段修改能够重新打开对应简报, so that 生成不是不可修改的死路。
28. As a 健康聊天用户, I want “什么时候训练合适”继续进入作息建议, so that 事实/建议问题不会被误当作计划修改。
29. As a 健康聊天用户, I want “晚上几点后停止锻炼”只返回作息事实, so that 不会出现餐食或动作资源污染。
30. As a 餐食计划用户, I want 裸“餐食计划”在已有计划上下文时得到新建/修改澄清, so that 系统不会擅自选择流程。
31. As a 健康聊天用户, I want 口语化同义表达与快捷问题进入相同任务, so that 不需要记住某个固定按钮文案。
32. As a 健康聊天用户, I want 无歧义输入不触发额外模型调用, so that 响应速度和结果稳定。
33. As a 健康聊天用户, I want 歧义输入经过一次受约束仲裁, so that 新建计划、修改计划、单次推荐和作息查询不会被随意混淆。
34. As a 健康聊天用户, I want 仲裁低置信时先被询问而不是被猜测执行, so that 错误任务不会修改我的状态。
35. As a 健康聊天用户, I want Agent 失败时已识别的合法槽位仍被保留, so that 模型故障不会丢失可确认信息。
36. As a 开发者, I want 共享路由只保留一个结构化判定实现, so that 新增一个修复不会再次造成关键词清单漂移。
37. As a 开发者, I want Trace 记录规则证据、仲裁来源和最终裁决, so that 无关输入触发错误任务时可以定位原因。
38. As a 开发者, I want 三个生成入口使用同一内部周锚点派生, so that 兼容字段不会在不同入口产生不一致日期。
39. As a 开发者, I want 时间适配和最终 Guard 分离, so that 自动调整不会削弱重叠、风险、资源和周范围校验。
40. As a 开发者, I want 旧会话和旧计划 API 保持可读写, so that 本轮不需要高风险数据库迁移。

## Implementation Decisions

- 继续使用健康聊天编排器作为最高业务接缝；不创建第二套计划或作息状态机。
- 将内部周锚点派生抽为无歧义、可复用的领域服务或纯函数，由餐食、训练、综合生成和聊天生成入口共同调用。派生函数以应用时区的当前日期计算周一；不得使用不同模块各自的“本周/下周”解析。
- 简报对象保留可序列化的日期兼容字段，但 `isComplete`、`missing`、`question`、`summary` 和动态 `supplementable` 不消费它作为用户必填项。生成前若简报没有锚点，服务端在同一请求内派生并传给计划持久化层。
- 会话 JSON 读取需兼容旧结构；新写入不得从用户消息日期更新内部锚点。若旧会话存在锚点，生成时必须保留该锚点，避免同一简报在重试或生命周期操作中漂移；若旧会话完全缺失才按统一规则补齐。实现时需明确“生成当天所在周”与幂等重放之间的优先级，幂等重放必须复用既有计划日期。
- 不新增数据库表或迁移；保留 `weekly_plan.week_start`、项目日期、版本快照和现有 API 字段。需要更新缺省日期注释、服务端校验入口和测试夹具。
- 新增餐训时间适配接缝，输入训练项目、餐食默认窗口、餐食时长和本地边界，输出重排后的餐食项目及结构化适配说明。该接缝必须是确定性、无 I/O、可单测的；组合器负责调用，`PlanValidationService` 负责最终不变量。
- 自动适配的餐食项目需要携带结构化来源/调整标记，或通过组合结果传递等价上下文，使 `MEAL_TIME_OUT_OF_WINDOW` 不再对成功适配结果发出误导告警。直接删除所有餐食窗口校验不在范围内。
- 同日调度使用 `[startTime,endTime)`，按训练起始时间稳定排序；候选时段先后顺序固定为默认窗口、训练后、训练前，且每一步都检查当天边界、已放置餐食和所有训练区间。
- 路由判定继续由共享 `HealthBriefRouter` 提供结构化结果，但新增“计划字段修改证据”应作为结构化状态条件，不是新增长关键词例外。路由器通过依赖注入构造，编排器、意图修订服务和测试使用同一个行为实例。
- 计划字段修改证据至少包含：计划生命周期可捕获、目标侧（MEAL/EXERCISE）、修改表达、对应字段解析成功，以及是否明确是事实/建议问句。只有字段解析成功才可压过“活动词 + 时间词”的泛化作息启发式。
- 裸计划词的“新建 vs 修改”歧义由状态策略先识别；已有同域计划上下文时返回澄清，不调用模型猜测。跨域或多任务从句才进入轻量仲裁 Agent。
- 意图仲裁 Agent 复用现有 Agent 合同和轻量模型职责，扩展受限输出 schema 和解析/复核逻辑；不让响应 Agent、计划 Agent 或作息事实模块承担任务路由职责。
- 规则先抽取合法槽位、否定和修改候选；Agent 仅仲裁焦点与任务候选。模型失败后必须沿用规则结果或返回澄清，不能退回旧的任意领域推荐兜底。
- 前端聊天摘要从结构化简报字段渲染时隐藏内部日期；计划页继续从计划 API 的技术日期渲染周一至周日和项目安排。需求指引卡片仅消费响应 `supplementable`。
- 前端不得自行派生周日期或默认周（含 nextMonday/本周/下周 类计算，避免历史时区错位复发）；聊天摘要、计划页网格和项目日期一律以服务端响应和计划 API 返回的既有日期字段渲染。
- 所有新增用户可见文案、Prompt 和代码注释遵守仓库中文约定；Trace 和内部字段可使用稳定英文枚举，但最终文案必须可理解。

## Testing Decisions

测试优先验证用户可见行为、任务/领域状态和计划不变量，不固定私有方法、Prompt 排版或实现调用次数，除非调用次数本身是本规格的性能/成本合同。

- 简报服务测试：训练/餐食简报缺少周锚点仍可完整；`missing` 不含 `weekStart`；日期输入不写入简报；旧会话缺锚点可兼容；摘要和指引隐藏日期。
- 统一周锚点测试：餐食、训练、综合三个入口在同一应用日期得到相同周一；已存在锚点优先保持；requestId 幂等重放不因日期变化生成第二组项目日期；计划页 API 仍返回具体日期。
- 动态指引测试：已填受支持菜系/餐食类型/口味/便利性后不再列出；全部可选项填满后没有“还可以补充”；未支持“中餐”同时出现“已记录，暂不按它筛选”和受支持菜系提示；未完整/INVALID/完整分支都使用同一动态列表。
- 路由单测：综合两侧完整时，“训练时间改为下午五到六点”“训练：调整为 17:00-18:00”“把训练安排到晚上七点”返回计划捕获；`activeSide=EXERCISE`、`escape=NONE`、原因可诊断。
- 路由反例测试：无计划上下文的“什么时候训练合适”“训练时段建议”以及有计划上下文的“晚上几点后停止锻炼”仍进入 `ROUTINE + RECOMMEND`；作息结果只含作息事实。
- 生命周期测试：已生成综合计划修改训练时间时重新打开训练侧简报；餐食侧字段不变；修改后重新出现生成入口；普通短句在 GENERATED/PAUSED 不被无条件捕获。
- 歧义仲裁测试：裸“餐食计划”在已有上下文时澄清新建/修改；明确快捷问题和同义表达不调用仲裁；多任务/否定/转折/指代输入最多一次仲裁；Agent 低置信、非法 JSON、超时和状态冲突时澄清且保留规则槽位。
- 路由共享实现测试：编排器、模型前续轮、模型后修正对同一输入产生相同结构化路由结论；生产注入实例和测试实例不因构造方式不同而漂移；Trace 包含 raw、规则修正、Agent 仲裁和最终路由原因。
- 餐训适配器单测：晚餐 `18:00-19:00` 与训练 `18:00-19:00` 自动调整到 `19:00-20:00`；训练后无法放置时训练前倒推；训练结束即餐合法；相邻区间合法；多训练按时间顺序；`05:00` 和 `24:00` 边界；跨午夜拒绝；无解时返回稳定错误。
- 餐训综合生成测试：训练时间保持用户输入；餐食移动记录在响应/metadata/Trace/版本说明；自动适配不产生 `SCHEDULE_OVERLAP` 或误导性 `MEAL_TIME_OUT_OF_WINDOW`；失败整体回滚，无半成品计划。
- 既有 Guard 回归：资源资格、年龄/风险、半小时粒度、零时长、跨午夜、跨周和适配器无解后仍存在的真实餐训重叠按原规则阻断；成功适配的窗口移动不作为冲突阻断；餐食-only/训练-only 不意外启用综合适配。
- Controller/真实 MySQL 测试：生成接口缺失周锚点仍成功；幂等重放使用相同日期；综合适配结果写入计划、版本和幂等快照；失败事务不留下项目或版本。
- 前端模块测试：聊天简报不渲染内部日期；动态可补充项只来自结构化响应；计划页仍显示周一至周日及具体安排；旧响应缺字段时不恢复全量固定指引。
- 真实浏览器验收必须覆盖运行中的同源应用：完整综合计划后修改训练时间、餐训冲突自动适配、生成说明可见、移动端无横向溢出；同时验证真正作息问句仍只显示作息事实。UI 变更遵守父级要求，记录 URL、输入、点击和结果。
- 既有路由/意图断言（含作息启发式优先、意图修订与模型调用次数类断言）和 health-eval-v2 评估快照中与本规格新合同冲突的条目更新为新合同并注明理由；其余回归保持原样，不通过删除断言、跳过门控或修改快照掩盖。
- 确定性/fixture 模式与正式模式对同一输入产生相同路由结论和同等动态指引结构；无模型路径不得出现两类模式分叉。
- 继续运行现有 Maven、MySQL 门控和前端测试；不通过删除旧断言、跳过门控或修改快照掩盖回归。Qdrant/真实模型仍保持独立环境门控。

## Out of Scope

- 不删除数据库中的 `weekStart`、`local_date` 或历史计划日期，也不重做计划页面的周网格模型。
- 不根据现实日期自动删除、归档、停用或隐藏计划；计划生命周期仍由用户操作决定。
- 不把用户输入的日期转换成新的用户需求字段、长期偏好或跨会话设置。
- 不允许餐食与训练重叠，不放宽风险、资源资格、时间粒度、跨午夜或周范围 Guard。
- 不建设自由形式的时间优化器、营养医疗处方、睡眠最佳训练时间事实或新的作息 RAG。
- 不让 Agent 决定训练日期、餐食时间、风险结论、资源资格或最终持久化动作。
- 不把所有请求都发送给 Agent；无歧义路径必须保留确定性快路径。
- 不以新增关键词例外取代结构化计划上下文判定，不新增分散的路由状态机。
- 不改造旧 `/api/v1/diet/**` 业务语义，不改变资源读取边界、匿名身份、计划生命周期枚举或现有前端框架。
- 不实现长期跨会话训练/餐食偏好记忆，不改变收藏和减少推荐的既有语义。
- 不在本规格内处理与本轮无关的媒体目录、RAG 语料或 `scripts/sync_local_media.py` 变更。

## Further Notes

- 当前工作树包含与本轮无关的 `scripts/sync_local_media.py` 修改和若干未跟踪餐食媒体文件；实施 agent 必须保留这些变更，不要回退或混入本修复提交。
- ADR-0018 已声明并在 ADR-0014 中标记为部分替代：餐训生成顺序和冲突适配规则改为训练优先，ADR-0014 的最终时间轴 Guard、半小时粒度、跨午夜和计划生命周期仍然有效，避免未来按旧文档恢复“冲突即拒绝”。
- `conversation-contracts` US 18、`plan-interaction-fixes` 的用户周起始日一致要求、`brief-supplement-loop` 的作息逃生口优先条款均已在 ADR-0018 声明被替代；实现和测试不得继续把它们当作现行用户语义。
- 目标周移除不是单纯删文案：生成服务、周范围持久化、旧会话兼容、计划页日期和幂等重放必须一起验证。尤其要避免“聊天隐藏日期但生成器仍要求 `weekStart`”这种半完成状态。
- 训练时间修改的最小回归必须使用用户原始短句，而不是只测试带完整计划摘要的长文本；否则会再次遗漏 Router 优先级问题。
- 餐食自动移动后的“窗口外”状态必须在用户可见说明中表达为系统适配结果，而不是风险或失败；若保留内部窗口元数据，应区分默认窗口和适配窗口。
- 建议实施切分：先完成 P0 动态指引和计划上下文路由，再完成 P1 周锚点统一和餐训适配，最后接入歧义仲裁。每个阶段先通过最高接缝自动化，再进行真实浏览器验收。
