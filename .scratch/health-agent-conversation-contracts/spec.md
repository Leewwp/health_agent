# 健康聊天显式任务路由与计划生成约束规格

Status: implemented / ready-for-human

实现状态：#104/#105/#106/#108 的代码、自动化测试与真实浏览器验收已完成；#107 输出独立研究文档（[`research/routine-grounded-docs-future.md`](research/routine-grounded-docs-future.md)）并明确本轮不实现。验收证据见各 issue 文件与 `docs/frontend-browser-acceptance.md`。

## Problem Statement

用户在餐食库或动作库按名称输入并回车时，页面可能只发生原生表单刷新而没有搜索结果。现有 API、Reader 和 SQL 已具备名称查询参数，但浏览页事件监听器按页面实例永久绑定到共享容器，旧页面实例、路由切换竞态或运行中的旧静态资源仍可能让 `submit` 事件未被拦截。当前没有前端回归测试证明“回车不刷新”和“跨页面切换后仍搜索”。

健康聊天还存在几类会直接破坏信任的行为：训练难度输入“入门 进阶”被静默截断为一个值；训练计划把“全身”当成任意部位，导致不满足部位约束的动作进入计划；严格条件下候选不足时没有清晰区分零候选与唯一候选；餐食计划在最小条件满足后没有稳定展示完整简报和补充入口，可能被普通推荐逻辑截断；作息问题可能跨域返回餐食卡；快捷问题不能完整覆盖当前主要业务流程。

这些现象的共同根因是：用户可见模式、领域任务、简报收集、推荐前预览、计划生成和资源候选约束没有形成单一且可验证的状态边界。旧文档中已有部分修复方案，但部分“确认简报”语义与本轮产品决定冲突，必须统一为无独立确认步骤的简报预览。

## Cross-Category Audit Coverage

本轮问题不能只按训练链路修复。对餐食推荐、餐食计划和综合计划做同构核对后，已有实现票 [#102](https://github.com/Leewwp/health_agent/issues/102) 中记录的边界也必须作为本规格的回归前置条件：餐食计划只能生成简报选择的 `mealTimes`，单餐或双餐时按所选餐次归一化每日热量；候选足够时七天内优先更换餐食，候选不足时允许最少重复；综合计划默认餐食→训练有序收集，共享目标可继承但两侧字段保持隔离，任一侧修改都只能更新该侧并重新展示生成入口。以上规则同时适用于餐食计划和综合计划，不能因显式任务路由或训练候选修复而回退。

单次餐食推荐继续保持 `mealTime` 最低槽位语义，不套用训练推荐的四项必填门槛；餐食推荐、餐食计划和综合计划必须分别断言领域、任务、阶段以及资源类型，避免修复一条链路时把另一条链路误改。

## Solution

保留现有健康聊天最高编排接缝和 `domain/task/phase` 正交模型，形成以下外部行为：

1. 新会话只有明确任务词才进入餐食推荐、训练动作推荐、餐食计划、训练计划或综合计划；不明确的短句不猜测领域，返回 `OTHER + CHAT` 或领域澄清。
2. 活动中的澄清或计划上下文允许短句继承当前领域；显式切换会暂停旧简报但不丢失，当前检索和澄清只消费当前领域投影。
3. 餐食和训练计划都先展示完整简报、可补充内容以及“开始生成/补充”操作。移除用户可见和持久化意义上的独立“确认简报”状态；开始生成时只校验当前完整简报并直接创建草稿。
4. 训练计划严格匹配“全身”动作标签。严格条件没有候选时不自动放宽；只有唯一候选时按用户指定训练日复用，并明确说明候选不足。
5. 难度是单选字段。多难度冲突保留已有值并提示“只能选择一个难度”，不得静默选择第一项或更保守项。
6. 作息事实问题只返回有来源的 `ROUTINE` 内容；“停止锻炼”本轮暂复用已有训练时段事实，文档/RAG 扩展另列未来任务。
7. 浏览页使用可销毁或唯一的事件委托边界，并通过真实浏览器和前端回归测试证明回车搜索不触发文档导航，跨餐食/动作页面切换后仍能正确发送 `q`。
8. 聊天快捷问题提供五个可扩展基础入口：餐食计划、训练计划、综合计划、餐食推荐、训练动作推荐。
9. 餐食计划和综合计划沿用 #102 已确认的餐次、热量和跨日软多样性约束；任何生成请求都必须消费当前简报，而不是固定三餐或陈旧子简报。

## User Stories

1. As a 健康聊天用户, I want 新会话输入餐食计划词时进入餐食简报, so that 我不会被追问训练条件。
2. As a 健康聊天用户, I want 新会话输入训练计划词时进入训练简报, so that 我不会被追问餐次或健康目标。
3. As a 健康聊天用户, I want 新会话输入综合计划词时进入综合简报, so that 餐食与训练可以按既定顺序收集。
4. As a 健康聊天用户, I want 新会话输入餐食推荐词时进入餐食推荐, so that 结果只包含餐食资源。
5. As a 健康聊天用户, I want 新会话输入训练动作推荐词时进入动作推荐, so that 结果只包含动作资源。
6. As a 健康聊天用户, I want 新会话输入“清淡一点”或“入门徒手”时不被猜测成某个领域, so that 系统不会误推荐错误类型内容。
7. As a 健康聊天用户, I want 在餐食澄清中明确切换训练, so that 餐食简报被暂停而不是丢失。
8. As a 健康聊天用户, I want 在训练澄清中明确切换餐食, so that 训练简报被暂停而不是污染餐食检索。
9. As a 健康聊天用户, I want 说“继续餐食计划”时恢复暂停的餐食简报, so that 我无需重新输入已收集条件。
10. As a 健康聊天用户, I want 当前领域检索只使用当前领域槽位, so that 旧品类的槽位和资源不会泄漏。
11. As a 健康聊天用户, I want 输入完整训练目标、部位、器材和难度后看到训练简报, so that 我能检查系统理解的条件。
12. As a 健康聊天用户, I want 输入完整餐次和健康目标后看到餐食简报, so that 我能检查系统理解的条件。
13. As a 健康聊天用户, I want 简报同时展示已整理条件和可补充条件, so that 我能决定是否继续完善。
14. As a 健康聊天用户, I want 看到“开始生成/补充”两个按钮, so that 我不必理解内部的简报确认概念。
15. As a 健康聊天用户, I want 点击开始生成直接校验并创建计划草稿, so that 计划流程不会被隐藏确认状态阻断。
16. As a 健康聊天用户, I want 生成前修改任一字段后使用最新简报, so that 旧条件不会被错误复用。
17. As a 健康聊天用户, I want 餐食计划只生成我选择的餐次, so that 计划不会静默扩大为固定三餐。
18. As a 健康聊天用户, I want 餐食计划默认当前周但可修改目标周, so that 简报既易用又可控。
19. As a 健康聊天用户, I want 餐食可选条件不阻断计划生成, so that 只提供最低条件也能完成流程。
20. As a 健康聊天用户, I want “入门 进阶”被识别为冲突, so that 系统不会静默丢弃我的一个选择。
21. As a 健康聊天用户, I want 已有入门难度时再次输入“入门 进阶”保留入门并提示只能选择一个, so that 原简报不会被破坏。
22. As a 健康聊天用户, I want “全身”只匹配明确的全身动作, so that 腿部或背部专属动作不会冒充全身动作。
23. As a 健康聊天用户, I want 严格条件没有候选时看到明确说明, so that 我知道结果为空不是系统故障。
24. As a 健康聊天用户, I want 零候选时看到追加或修改条件入口, so that 我可以主动决定如何放宽需求。
25. As a 健康聊天用户, I want 只有一个候选动作时仍能覆盖指定训练日, so that 小概率数据稀缺不会阻断计划。
26. As a 健康聊天用户, I want 唯一动作复用时看到候选不足提示, so that 我理解重复安排的原因。
27. As a 健康聊天用户, I want 系统不自动放宽训练部位、器材、难度、目标或风险条件, so that 计划始终符合我确认的硬约束。
28. As a 健康聊天用户, I want 作息问题只返回作息事实卡, so that “停止锻炼”不会突然返回餐食。
29. As a 健康聊天用户, I want 作息事实包含来源信息, so that 我能判断建议依据。
30. As a 健康聊天用户, I want 暂时没有事实覆盖的问题得到边界说明, so that 系统不会编造固定时间。
31. As a 健康聊天用户, I want 快捷问题包含餐食计划入口, so that 我能快速开始主要流程。
32. As a 健康聊天用户, I want 快捷问题包含训练计划入口, so that 我能快速开始主要流程。
33. As a 健康聊天用户, I want 快捷问题包含综合计划入口, so that 我能快速开始主要流程。
34. As a 健康聊天用户, I want 快捷问题包含餐食推荐入口, so that 我能快速获取单次餐食建议。
35. As a 健康聊天用户, I want 快捷问题包含训练动作推荐入口, so that 我能快速获取单次动作建议。
36. As a 资源库用户, I want 在餐食库名称框回车只触发 API 搜索, so that 页面不会刷新丢失输入。
37. As a 资源库用户, I want 在动作库名称框回车只触发 API 搜索, so that 页面不会刷新丢失输入。
38. As a 资源库用户, I want 餐食库与动作库切换后仍能搜索, so that 页面监听器不会串扰。
39. As a 开发者, I want 所有领域检索消费投影后的槽位, so that 跨域回归可通过统一接缝验证。
40. As a 开发者, I want 计划生成只消费当前简报快照, so that 请求重试不会使用陈旧字段。
41. As a 开发者, I want 计划生成不依赖用户可见确认字段, so that 前端动作和后端状态不会出现隐藏阶段。
42. As a 开发者, I want 候选白名单和硬约束由确定性代码校验, so that Agent 不能注入越界动作。
43. As a 开发者, I want 规则降级和模型路径共享同一归一化结果, so that 难度冲突和别名行为一致。
44. As a 开发者, I want 前端监听器可销毁或由唯一路由委托管理, so that 多次导航不会累积旧处理器。
45. As a 开发者, I want 自动化测试断言领域、任务、阶段和资源类型, so that 文案调整不会掩盖跨域错误。
46. As a 开发者, I want 未来作息文档/RAG 作为独立任务管理, so that 本轮路由修复不扩大为新的检索系统。
47. As a 餐食计划用户, I want 只生成简报中选择的餐次, so that 生成结果不会静默扩展为固定三餐。
48. As a 餐食计划用户, I want 单餐或双餐时按所选餐次归一化热量, so that 计划预算与我的选择一致。
49. As a 餐食计划用户, I want 候选足够时七天内优先更换餐食, so that 餐食计划不会无理由重复同一组资源。
50. As a 综合计划用户, I want 餐食与训练按有序阶段收集且共享目标可继承, so that 两侧不会交替追问或互相污染。
51. As a 综合计划用户, I want 修改一侧简报只影响该侧并重新展示生成入口, so that 另一侧条件不会被错误清空或使用旧快照。

## Implementation Decisions

- 继续使用健康聊天 Controller 到 HealthOrchestratorService 的单一最高测试接缝；不建立平行聊天服务或第二套状态机。
- 保留 `domain/task/riskFlags/phase` 正交模型，新增任务入口只通过现有 `OTHER + CHAT`、`MEAL/EXERCISE/ROUTINE` 和 `COMPOSITE + PLAN` 组合表达。
- 新会话必须有明确领域/任务证据；活动澄清上下文只允许短答继承当前域、任务和阶段，不继承其他领域槽位。
- 显式切换领域暂停当前计划简报但不清空；恢复必须使用明确的继续计划表达。当前领域投影是推荐、澄清和候选读取的唯一输入。
- 计划简报保留结构化字段和完整性校验，但移除独立的用户确认动作、确认版本和“已确认才能生成”的状态依赖。开始生成操作直接提交当前完整简报，服务端重读会话后校验字段并创建草稿。
- 餐食和训练简报均展示摘要与可补充项；餐食默认当前周，餐次与健康目标为最低条件，菜系/口味/便利性等为可选条件。
- 训练难度保持单值。归一化发现多个合法难度时返回冲突；若已有合法难度则保留原值并提示“只能选择一个难度”，没有已有值时要求重新选择。
- “全身”严格匹配归一后的动作 `bodyParts` 标签；不根据名称、辅助肌群或模型推断补全全身资格。
- 严格候选为计划资格、部位、器材、难度、目标和硬约束的交集。零候选不自动放宽并提供追加/修改条件；唯一候选允许按指定训练日复用并明确说明。
- 推荐前预览按钮命名为“开始推荐”和“补充”，不再使用用户不可理解的“确认推荐”措辞；计划按钮同理命名为“开始生成”和“补充”。
- 作息本轮沿用已核验的结构化事实 Provider；“停止锻炼”复用训练时段事实口径，未来再评估文档证据检索或 RAG 扩展，不新增 schema。
- 快捷问题采用可扩展配置，首批固定五个入口：餐食计划、训练计划、综合计划、餐食推荐、训练动作推荐。
- 浏览页事件处理改为单一可管理的路由委托或显式销毁，必须保留 `preventDefault`、当前路由判断和 `q` 参数契约；不得通过修改 SQL 放宽或替换搜索语义。
- 不修改资源 Provider/Reader 边界，不让意图修复绕过审核资源读取；不修改旧饮食链路。
- 餐食/综合生成复用 #102 已定义的餐次集合、按所选餐次归一化热量和跨日软多样性；显式任务路由修复不得改变这些生成不变量。
- 不新增数据库迁移；若现有持久化字段仅服务于用户可见确认步骤，应在兼容现有数据读取的前提下移除写入和生成依赖，并记录迁移/清理策略。

## Testing Decisions

- 最高接缝为 `POST /api/v1/health/chat` 的完整轮次测试，断言 `responseType`、`domain`、`task`、`phase`、`missingSlots`、按钮动作和资源类型；不锁定易变的模型措辞。
- 增加训练简报冲突矩阵：首次输入多难度、已有难度后的多难度、未知难度、规范单值；断言保留/澄清行为。
- 增加训练候选矩阵：严格全身命中、单部位排除、零候选、唯一候选、多日复用和不自动放宽；断言每个计划项目的候选 ID 与用户条件一致。
- 增加餐食/训练计划共同的“摘要 → 开始生成/补充”外部契约测试，断言不存在确认动作和确认阶段；生成请求只能消费当前完整简报。
- 增加跨域会话测试：餐食暂停后切训练、训练暂停后切餐食、明确恢复、旧槽位不进入当前模块、作息问题不返回餐食或动作卡。
- 增加 `OTHER + CHAT` 测试覆盖新会话模糊短句和无关问题；明确任务词仍必须进入目标流程。
- 增加前端模块测试：首次搜索、回车 `preventDefault`、请求含 `q`、餐食↔动作切换后搜索、监听器销毁/唯一委托；必要时使用真实 Chromium 检查 Network 无文档导航。
- 增加 Controller/Reader 搜索参数透传测试，保留 SQL `name/name_en` 语义和审核边界；不以扩大搜索范围代替修复。
- 增加餐食/综合同构回归：餐食推荐仍只需 `mealTime` 最低条件；餐食计划只生成选择餐次并校验热量归一化；综合计划按餐食→训练阶段收集、共享目标继承且单侧修改不影响另一侧。
- 增加作息事实类型测试：咖啡因与训练时段问题只返回 `ROUTINE` 和来源；无事实时返回边界说明。
- 复用现有 `HealthOrchestratorServiceTest`、`IntentRuleServiceTest`、`PlanBriefServiceTest`、`TrainingPlanGenerationServiceTest`、浏览器验收脚本和前端 Node 测试作为先例。
- 必须执行 `mvn -DskipTests compile`、聚焦 Maven 测试、`mvn test`、前端 Node 测试、`docker compose config --quiet`，并在重启后的本地同源入口执行真实浏览器验收。

## Out of Scope

- 本轮不接入新的作息文档库、通用 NLP、向量 RAG 或第二模型服务；只记录未来方向并保留当前已核验事实。
- 不自动放宽训练部位、器材、难度、目标、风险或审核资格，也不扩充动作数据集来掩盖零候选。
- 不重写资源 Provider/Reader 架构，不修改旧 `/api/v1/diet/**` 链路，不引入 React/Vue/Vite/Node 构建链。
- 不把“全身”解释为任意单部位组合；是否允许分部位覆盖属于后续显式产品能力，不在本轮隐式启用。
- 不保留用户可见的简报确认按钮、确认文案、确认阶段或确认版本；服务端只保留必要的当前请求一致性与计划写入幂等校验。
- 不新增作息个性化计划算法，不把停止锻炼问题转成训练动作推荐或训练计划澄清。
- 不重开已关闭的 #78、#82、#101 或改变 #102 的历史结论；本轮建立新问题单承载回归和语义变更。

## Further Notes

- 当前工作树包含上一批计划交互修复的未提交改动，实施前必须区分这些改动与本规格的新行为，尤其是计划确认字段、全身候选和前端浏览监听器。
- 运行中的旧后端或旧前端容器可能复现历史错误；验收必须在重启后的同源入口完成，并记录实际加载的静态资源与 Network 请求。
- 作息未来方向可拆为研究任务：盘点已核验文档、定义主题/来源/版本模型、评估结构化事实与 RAG 的边界，再决定是否实现。
