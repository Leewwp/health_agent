# 健康 Agent 动作数据、推荐前确认、个人收藏与“我的计划”重构规格

Status: ready-for-agent
Type: spec
Date: 2026-08-21

## Problem Statement

健康 Agent 当前存在四个相互影响的用户问题。

第一，动作详情出现训练部位、目标肌群和步骤缺失。核对 `/Users/pp/Downloads/exercises.json`（2026-08-21 本地文件）确认共有 1324 条记录，`name`、`category`、`body_part`、`equipment`、`target`、`muscle_group`、`secondary_muscles` 和多语言 `instructions` 存在；但该文件的 `images` 与 `gif` 字段在 1324 条记录中均为空/缺失，也没有 `difficulty`、`movement_pattern` 或 `risk_tags` 原始字段。因而缺失不能全部归因于本地导入：中文步骤可从 `instructions.zh` 生成，媒体和训练资格必须分别按许可状态与确定性规则补充，禁止伪造为源数据。当前数据库还把多个动作语义压缩或遗漏，无法让用户验证动作推荐是否合理。

第二，餐食推荐和动作推荐可能在只识别出少量条件后直接开始。用户希望系统在最低条件满足后先展示已确认需求，并给出一次明确的“为我推荐”确认；未确认的其他槽位可以继续补充，但不强制填满全部槽位。该确认应复用现有推荐请求，不成为新的推荐类型；“换一批”仍表示保留当前需求并排除已展示资源后的替代推荐。

第三，当前“收藏”仍与旧推荐反馈事件耦合，餐食页和动作页缺少统一的“仅看收藏”，计划候选只加载有限结果后在前端过滤。用户需要一个独立的个人资源集合，用于在计划编辑时快速找到喜欢的餐食和动作。收藏不代表采纳、使用、加入计划或提高推荐排序。

第四，当前“我的计划”仍接近列表和大下拉框编辑，无法形成高效的周计划工作流。用户需要一个完整的日程式页面：周视图、半小时时间轴、空白时间段新增、资源搜索/筛选弹窗、详情抽屉、替换/删除/移动、未保存批量保存，以及适配移动端的单日时间轴。资源事实和用户计划处方必须分开，餐食热量等资源事实不应被任意编辑。

## Solution

建立一条从权威动作数据到可验证资源详情，再到可编辑综合周计划的完整链路：

1. 以 `exercises.json` 为权威源，按 `(source_name, source_id)` 幂等导入全部 1324 条动作，保留数据库内部 ID；保留 `category`、`body_part`、`target`、`muscle_group`、`secondary_muscles`、`equipment`、原始多语言 instructions 等独立来源字段。
2. 为部位、器材、主要目标肌群和协同肌群建立完整确定性中文映射；原始英文保留为来源字段，导入报告记录未映射值和字段变化。
3. 将动作资格分为可浏览、可单次推荐和可进入周计划三个层级；原始动作字段不由 Agent 或模型生成。
4. 在健康聊天状态机中增加推荐前确认阶段。最低条件满足时显示已确认槽位、可补充槽位以及“为我推荐/继续补充需求”；用户确认后继续现有推荐通道。
5. 建立独立个人收藏集合接口和持久化模型。餐食浏览、动作浏览、推荐卡片和计划资源弹窗统一读取该集合；旧反馈历史保留给评估和审计，不作为新收藏来源。
6. 将“我的计划”重构为混合 TimeGrid 页面：桌面周视图、移动端单日视图、半小时网格、资源选择弹窗、项目详情抽屉、显式批量保存。第一阶段支持点击新增和点击移动，第二阶段增加桌面拖拽吸附。
7. 延续 ADR-0014 的综合周计划生命周期和服务端校验：计划可包含餐食与动作，项目时间统一校验，已启用计划编辑创建副本，保存和启用分离。

## User Stories

### 动作数据和详情

1. As a 健康 Agent 用户, I want to看到动作的训练部位, so that我能判断推荐是否符合我的目标。
2. As a 健康 Agent 用户, I want to看到主要目标肌群和协同肌群, so that我能验证动作刺激范围。
3. As a 健康 Agent 用户, I want to看到完整中文步骤, so that我能理解如何执行动作。
4. As a 健康 Agent 用户, I want to看到器材、难度和动作模式, so that我能判断动作是否适合当前条件。
5. As a 健康 Agent 用户, I want to看到动作图片、GIF 和媒体署名, so that我能识别动作并了解来源。
6. As a 健康 Agent 用户, I want to看到原始字段和中文标签来源状态, so that我不会把系统翻译误认为数据集原文。
7. As a 项目维护者, I want to用 dry-run 报告动作导入差异, so that我能在应用数据前发现字段丢失和映射错误。
8. As a 项目维护者, I want to重复导入同一数据集不改变资源内部 ID, so that已有计划和反馈不会失效。
9. As a 项目维护者, I want to知道哪些动作只能浏览、哪些可以推荐、哪些可以入计划, so that目录扩容不会绕过安全校验。
10. As a 项目维护者, I want to看到未映射标签报告, so that中文化工作可以持续补齐而不是静默混用中英文。

### 推荐前确认

11. As a 餐食推荐用户, I want to在最低需求满足后看到已确认餐次、健康目标和口味, so that我能确认 Agent 理解正确。
12. As a 餐食推荐用户, I want to在确认前补充菜系、场景或便捷需求, so that我可以改善结果而不被强制填写所有槽位。
13. As a 餐食推荐用户, I want to点击“为我推荐”继续当前推荐流程, so that我不需要重新描述需求。
14. As a 动作推荐用户, I want to在推荐前确认部位、器材、目标和难度, so that我能避免不符合条件的动作。
15. As a 用户, I want to用自然语言表达“可以推荐了”, so that按钮不是唯一的确认方式。
16. As a 用户, I want to修改已确认槽位后重新看到确认状态, so that旧结果不会误用新需求。
17. As a 用户, I want to点击“换一批”时沿用已确认需求, so that替代结果不重复追问。
18. As a 用户, I want to看到候选耗尽的明确结果, so that系统不会静默放宽我的需求。

### 个人收藏集合

19. As a 用户, I want to收藏餐食资源, so that我能在计划编辑时快速找到它。
20. As a 用户, I want to收藏动作资源, so that我能建立自己的训练候选集合。
21. As a 用户, I want to在餐食页只看收藏, so that我不必翻阅整个资源库。
22. As a 用户, I want to在动作页只看收藏, so that我能快速筛选喜欢的动作。
23. As a 用户, I want to在计划资源弹窗中只看收藏, so that替换项目时选择成本更低。
24. As a 用户, I want to在不同页面看到一致的收藏状态, so that收藏不会因页面不同而产生分歧。
25. As a 用户, I want to取消收藏, so that我的个人集合可以持续维护。
26. As a 用户, I want to收藏不自动提升 Agent 排序, so that资源管理和推荐偏好保持独立。
27. As a 评估人员, I want to保留旧反馈历史, so that历史评估和 Trace 归因不因收藏重构丢失。

### 综合周计划

28. As a 用户, I want to看到计划名称、周范围和生命周期状态, so that我能区分草稿、未启用、已启用和历史计划。
29. As a 用户, I want to在一张周表中查看餐食和动作, so that我能理解全天安排。
30. As a 用户, I want to切换全部、餐食和动作, so that我能聚焦当前任务。
31. As a 用户, I want to按半小时查看时间, so that我能准确安排餐食和训练。
32. As a 用户, I want to在桌面端看到 7 天横向时间轴, so that我能比较一周安排。
33. As a 移动端用户, I want to以单日时间轴查看计划, so that页面不会把 7 天压缩到无法使用。
34. As a 用户, I want to点击空白时间段新增项目, so that我可以直接在目标时间安排内容。
35. As a 用户, I want to搜索餐食或动作, so that我不必从巨大下拉框中寻找资源。
36. As a 用户, I want to使用结构化筛选和仅看收藏, so that我能快速缩小候选范围。
37. As a 用户, I want to从弹窗选择资源后打开计划编辑抽屉, so that资源选择和处方编辑职责清晰。
38. As a 用户, I want to替换计划中的餐食或动作, so that我能保留时间安排并更换内容。
39. As a 用户, I want to删除计划项目, so that我可以清理不需要的安排。
40. As a 用户, I want to移动项目日期和时间, so that计划符合实际日程。
41. As a 用户, I want to在移动端通过选择项目和目标时间格移动, so that触控不会和长按拖拽冲突。
42. As a 用户, I want to在桌面端拖拽项目并吸附到半小时, so that移动重复训练更高效。
43. As a 用户, I want to编辑动作时长、组数和次数, so that确定性训练处方可以做小幅调整。
44. As a 用户, I want to不能手工覆盖餐食资源热量, so that计划不会产生与资源事实冲突的数据。
45. As a 用户, I want to一次保存多项计划调整, so that中间操作不会产生难以理解的半成品。
46. As a 用户, I want to取消未保存编辑, so that误操作不会影响计划。
47. As a 用户, I want to看到时间重叠错误, so that系统不会静默覆盖餐食或训练。
48. As a 用户, I want to编辑已启用计划时自动得到副本, so that当前执行计划保持稳定。
49. As a 用户, I want to显式启用保存后的计划, so that保存和实际使用不会混淆。
50. As a 用户, I want to查看、复制和删除历史计划, so that计划生命周期完整可控。

## Implementation Decisions

### 1. 动作权威导入

- 新增独立的动作数据导入/校验 seam，支持 dry-run 和 apply 两种模式。
- 导入源是完整 `exercises.json`，当前基线为 1324 条。
- `(source_name, source_id)` 是 Upsert 身份；已有记录保留数据库内部 ID。
- 不直接删表重建；源文件中消失的记录先进入差异报告，由显式清理操作处理。
- 原始字段必须独立保存，至少覆盖 category、body_part、target、muscle_group、secondary_muscles、equipment、原始 instructions 和源媒体字段。`difficulty`、`movement_pattern`、`risk_tags`、中文标签和 `plan_ready` 是派生/审核字段，必须与原始字段分列保存并记录生成规则与版本。
- 原始英文值保留；核心标签使用确定性中文映射表导入。映射表应版本化，未映射值不得由模型翻译。源文件没有可用图片/GIF 时，媒体状态必须为 `NONE`，不得从空字段推断 URL；只有独立、可核验且具许可的媒体目录才能填充媒体与署名。
- 导入报告包含总数、新增、更新、保留 ID、字段变化、缺失字段、未映射标签、源版本或哈希、可浏览/可推荐/可入计划资格统计。
- 资源资格分为 `VISIBLE`、`RECOMMENDABLE`、`PLAN_READY` 语义层级；Agent 只能消费候选白名单，不能创建资源字段或训练剂量。
- 动作媒体继续遵守来源署名和明确媒体状态规则。

### 2. 推荐前确认

- 扩展现有健康聊天会话状态，增加 `Recommendation Preflight` 阶段。
- 普通推荐只要求最低条件，不要求 7 个餐食槽位或全部健身槽位都填写。
- 状态中保留已确认槽位、可选未确认槽位和用户是否明确确认。
- “为我推荐”复用现有推荐请求，不新增独立推荐域；请求可携带明确确认标记。
- 用户补充或修改槽位后，确认标记重置，重新展示确认摘要。
- 用户自然语言表达“可以推荐了”与按钮行为一致。
- “换一批”复用当前任务上下文和累积排除集合，不重复进入推荐前确认。
- 推荐前确认仅属于当前任务，不写入长期偏好或个人收藏集合。

### 3. 个人收藏集合

- 新增独立的收藏存储和服务边界，资源身份使用 `(userId, resourceType, resourceId)` 唯一键。
- 现有匿名演示身份作为收藏归属，不与会话绑定。
- 提供添加、取消、分页查询和按资源类型/收藏状态筛选能力。
- 餐食浏览、动作浏览、推荐卡片和计划候选弹窗共用同一服务边界。
- 旧 `FAVORITE/UNFAVORITE` 反馈不迁移为新集合；旧反馈表保留历史评估、审计和兼容读取用途。
- 收藏不得自动进入推荐重排，不与 `REDUCE_RECOMMENDATION` 混合。
- 前端可以乐观显示，但服务端集合是真实来源；失败时必须回滚显示。

### 4. 计划后端和领域边界

- 延续统一综合周计划、四态生命周期、版本和幂等写入模型。
- 项目批量保存是新增、替换、删除、移动和处方调整的统一写入 seam。
- 所有项目共享时间冲突校验，时间区间是左闭右开 `[startTime,endTime)`；时间必须是整点或半点，跨午夜、跨周和重叠拒绝。
- 餐食项目参数不允许用户手工覆盖资源热量；资源热量从审核资源读取。
- 动作项目允许用户编辑 duration、sets、reps，仍需正值和计划校验。
- 资源替换后，动作处方按确定性规则重新计算；Agent 不自由生成训练剂量。
- 编辑 `ENABLED` 计划先创建编辑副本，保存后保持 `UNENABLED`，用户需显式启用。
- `HISTORY` 计划只读，可复制为草稿；当前演示允许经过确认后物理删除历史计划，但不删除资源或反馈审计数据。

### 5. “我的计划”前端原型和页面

- 保持 vanilla ES Modules、hash 路由和现有前端共享 UI，不引入 Vue/React/Vite。
- 页面以工作区和时间轴为中心，不使用营销式布局或巨大下拉框。
- 桌面端采用 7 天横向列、时间纵向轴的 TimeGrid；默认滚动到约 06:00-22:00，全天可访问。
- 移动端采用单日时间轴和日期切换，避免横向溢出。
- 页面状态包括列表、空列表、加载、错误、DRAFT、UNENABLED、ENABLED、HISTORY、未保存和保存失败。
- 详情头部显示名称、周范围、状态和状态允许的操作；保存和启用必须分开。
- 提供“全部/餐食/动作”分段筛选。
- 空白格点击打开资源选择弹窗；弹窗提供类型切换、搜索、结构化筛选、仅看收藏、分页和资源卡片。
- 资源卡片可预览详情，明确的选择动作才加入项目；弹窗关闭后保留筛选上下文。
- 资源选择后打开项目详情抽屉；抽屉分离只读资源事实和可编辑计划字段。
- 餐食编辑只包含日期、时间和备注；动作编辑还包含时长、组数和次数。
- 项目新增、替换、删除、移动全部进入本地未保存集合；页面显示保存/取消和离开确认。
- 移动端第一阶段使用选择项目后点击目标时间格；桌面拖拽吸附为第二阶段，调用同一移动保存 seam。
- 事件块显示类型、名称、时间和关键参数，文本必须有稳定布局和移动端适配。
- 资源详情复用现有审核 Reader 详情加载边界，不让计划页面绕过审核资源边界。

#### 5.1 已确认原型方案（2026-08-21）

- 原型唯一入口为 `#/prototype/my-plan`；此前用于比较的 A/B/C 变体入口和渲染分支不再保留。
- 原型采用“可折叠计划库侧栏 + 横向七日卡片工作区”。计划库默认展开，控制行同时提供折叠计划库、计划库标题和新建计划。
- 侧栏折叠后保留窄栏，包含展开按钮、新建计划按钮和每个计划的状态点/符号；按钮和状态点必须提供悬停提示，说明功能、计划名称或状态。
- 折叠状态下点击计划图标先展开侧栏，再切换计划；点击新建计划先展开侧栏，再进入草稿计划。
- 展开侧栏时，七日工作区允许水平、垂直滚动，周六和周日通过水平滚动查看；折叠侧栏时取消工作区固定最小宽度，七列自适应可用宽度，桌面端无需水平滚动即可看到完整周计划。
- 折叠窄栏直接融入页面背景，不使用独立深色底或强边框；仅保留轻量边界和选中态。
- 七日工作区以周一至周日完整横向布局呈现，项目按日期分组为卡片；保留“全部 / 餐食 / 动作”筛选。
- 餐食和动作使用不同颜色，但必须同时显示“餐食/动作”文字标识，不能只依赖颜色。
- 原型保留点击项目打开详情抽屉、点击日期空白打开资源选择弹窗、资源搜索/类型切换/仅看收藏/替换资源、项目删除、快速移动、批量保存/取消和未保存提示。
- 原型使用内存 fixture，不连接新后端接口；它只冻结信息架构和交互模型，生产实现必须接回现有计划服务、审核 Reader 和独立收藏集合边界。
- 原型代码和样式分别位于现有前端页面模块和共享样式文件；后续生产实现应在不改变用户可见交互决策的前提下替换 fixture 状态和模拟动作。

### 6. 实施顺序

1. 动作导入字段审计、映射表、dry-run/apply 和导入报告。
2. 动作数据库字段、Reader、详情 API 和页面字段接入。
3. 独立个人收藏集合和分页筛选接口。
4. 餐食页、动作页、推荐卡片和计划候选弹窗接入收藏集合。
5. 健康聊天推荐前确认状态和按钮/自然语言确认。
6. 计划后端参数白名单、历史删除和资源事实/处方边界调整。
7. 以已确认原型为基线接入“我的计划”生产数据：计划库侧栏、七日工作区、状态操作和资源详情边界。
8. 接入资源选择弹窗、独立收藏集合、详情抽屉和批量保存；保留原型的筛选、替换、删除、快速移动和未保存状态。
9. 补齐移动端单日时间轴或等价的窄屏日期工作区；原型的七日卡片布局不得在移动端产生横向溢出。
10. 桌面拖拽吸附专项；必须复用已有移动/批量保存校验 seam。
11. 自动化测试、真实浏览器验收和文档/ADR 冲突修订。

## Testing Decisions

- 测试优先验证外部行为、领域契约和失败路径，不断言私有 helper、具体 HTML 结构或 Agent 文案。
- 最高测试 seam 是健康聊天 API/HealthOrchestratorService：验证推荐前确认、槽位修改重置、确认后推荐和“换一批”排除集合。
- 动作导入 seam 验证 1324 条基线、幂等 Upsert、内部 ID 保留、中文映射覆盖、未映射报告、字段完整性和三层资格统计。
- Reader/API seam 验证动作详情独立字段、中文步骤、媒体状态、来源署名和缺失资源行为。
- 收藏集合 seam 验证按匿名用户隔离、添加/取消幂等、分页、资源类型隔离、仅看收藏和失败回滚；旧反馈保留不影响新集合。
- 计划服务 seam 验证餐食热量不可任意覆盖、动作处方正值校验、项目批量保存、时间重叠/跨周/跨午夜拒绝、版本冲突、历史删除和已启用编辑副本。
- 前端模块测试验证计划状态按钮互斥、TimeGrid 筛选、空白格新增、资源弹窗搜索/收藏筛选、详情抽屉字段、未保存取消、批量保存失败回滚和移动端点击移动。
- 桌面拖拽测试验证最近半小时吸附、时间边界和冲突错误；该能力可作为第二阶段专项。
- 真实浏览器验收覆盖桌面周视图、移动单日视图、资源弹窗、详情抽屉、收藏筛选、新增/替换/删除/移动、历史删除和无横向溢出。
- 现有 prior art：统一计划生命周期测试、计划批量项目测试、资源 Reader 测试、HealthOrchestratorService 测试、PreferenceService 测试、前端资源卡交互测试和 `docs/frontend-browser-acceptance.md`。
- MySQL 门控覆盖新字段迁移、动作 Upsert、收藏集合唯一约束和计划事务；Qdrant 与真实模型不是本地核心闭环前置条件。

## Out of Scope

- 不使用 Agent 或离线模型生成动作原始元数据、中文标签、风险规则或训练剂量。
- 不实现专业人工逐条审核 1324 条动作。
- 不把收藏自动转成推荐倾向或排序提升。
- 不把普通聊天直接作为已保存计划的隐式修改入口。
- 不允许餐食计划项目手工覆盖资源营养事实。
- 不实现月历、日历同步、提醒、打卡、穿戴设备或长期执行追踪。
- 不在第一阶段实现桌面拖拽；先完成点击移动和完整保存语义。
- 不重写前端框架，不引入构建链。
- 不删除 `recommend_feedback` 历史表作为收藏重构的一部分。
- 不把源文件消失的动作自动物理删除；清理必须是独立的显式操作。
