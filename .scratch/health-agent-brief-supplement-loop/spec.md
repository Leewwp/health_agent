## Problem Statement

用户在与健康助手完成计划简报收集（如"目标周、餐次、目标增肌已确认"）后，追加偏好时连续遇到四类失败：

1. **不知道能补充什么**。简报完成后系统只说"可以直接开始生成，或继续补充"，不列举可补充的属性；前端"补充"按钮点击后也没有任何提示，用户无从下手。
2. **补充被误判为单次推荐**。输入"我喜欢清淡的餐食"（本意是为计划补充口味），系统却按"领域 MEAL · 任务 RECOMMEND"走了一次独立推荐检索，偏好没有进入计划简报。
3. **补充被整体丢弃且提示不可理解**。输入"我喜欢中餐，由于在上班，每天做饭时间有限，希望烹饪时间短一些"，系统回复"我会在当前对话中继续完成计划生成。请先整理需求简报，完成后即可开始生成训练、餐食或综合计划"——用户不知道哪里错了，也不理解什么是"整理需求简报"；中餐与烹饪时长两项偏好完全丢失。
4. **推荐前条件确认被跳过**。新会话输入"今晚想吃得清淡一点，有什么推荐？"，系统在条件已足够时直接返回推荐结果。按设计，五条主流程（餐食计划、训练计划、综合计划、餐食推荐、训练动作推荐）都应先列举当前已确认条件与可补充条件，让用户选择"基于当前条件开始"或继续补充。

已逐条核实的根因（按层）：

- **路由层**：会话中"计划简报会话活跃"这一状态没有成为路由证据，路由完全依赖当轮文本与多份手工关键词清单。同一句补充，因含不含某个词会得到三种不同错误结果：被降级为 RECOMMEND（含"餐食/清淡"等领域词）、落进看不懂的 PLAN 兜底通知（不含领域词）、或侥幸进入简报（恰好含"确认/改成/目标周"）。意图修正服务内部至少有六份口径互相漂移的关键词清单（计划续轮词、推荐请求词两份副本、简报续轮词、综合简报回复词、餐食/训练简报输入词），这是问题反复出现、修 A 坏 B 的结构性原因。
- **数据层**：餐食计划简报只有目标周、餐次、健康目标三个字段，没有菜系、口味、便利性字段，解析器也只认这三样——上一轮规格（conversation-contracts）明确要求"菜系/口味/便利性等为可选条件"，实现遗漏。词汇层同样有洞：菜系别名没有"中餐"（库中也确实无此标签），便利性别名没有"烹饪时间短/做饭时间有限/快手"（而库内有"快速"223 条、"快手"10 条，本可映射）。
- **预检层**：推荐前预检机制存在且内容正确（已确认条件 + 可补充槽位 + 两个动作），但触发条件被实现为"候选数大于 2"，候选只有一两个时整个确认阶段被跳过——上一轮规格只规定了按钮命名，从未支持该门槛。
- **文案层**：简报完成分支文案为写死字符串，不含可补充项枚举；前端"补充"按钮只聚焦输入框。

## Solution

以一个状态原则收口：**把"计划简报会话活跃"变成一等路由证据，路由判定收敛为单一共享实现并返回结构化判定结果，判定优先级是固定合同**；关键词只保留两个逃生口（明确推荐请求、明确切换领域/作息提问）。在此之上分四层修复：

1. **统一续轮判定**：简报会话活跃时，自由文本一律进入对应简报处理器（补充/修改条件），明确推荐请求词放行去单次推荐，明确切域与作息提问交完整意图链；新会话模糊短句仍走领域澄清（不回退显式任务路由）。综合计划由结构化判定额外给出**活跃侧归属**（MEAL/EXERCISE/BOTH/NONE）。简报会话有显式生命周期（OPEN/PAUSED/GENERATED），**独立计划生成服务在持久化成功后负责关闭对应范围的会话**。
2. **餐食简报可选偏好**：简报新增菜系、口味/营养偏好、便利性字段与**未支持偏好**集合；解析由归一器词表（受支持集合）加一个**确定性的受限菜系意图解析器**（不依赖模型、不参与路由）组成；"中餐"这类库中无标签的偏好按未支持状态记录、展示并进入生成说明，但不参与过滤；单选字段冲突语义与既有难度单选模式一致。
3. **生成侧消费**：计划餐食候选扩展受控偏好标签（审核库读既有数据列；fixture 种子补充确定性标签表），生成时优先选取满足偏好的候选；偏好导致当日候选不足时**整天回退**，并在计划 metadata、计划 API（`PlanView` 结构化 `generationNotes` 字段）与计划页说明中标注未满足的偏好（回退可见，不静默放宽）；无偏好时生成行为与现状一致，最低条件即可生成。
4. **文案与预检**：三个简报完成分支统一输出"还可以补充：……"枚举（通过稳定的响应字段下发给前端，渲染为可点参考项）；推荐前预检改为设计驱动（候选非空即预检，仅豁免 ADJUST/替代推荐/已确认/作息事实），按钮命名对齐 ADR-0016 规范标签。

配套一组回归矩阵测试与真实浏览器验收，防止第三次复发。

## User Stories

1. As a 餐食计划用户, I want 简报收集期间直接说口味、菜系等偏好时被写入餐食简报, so that 补充条件不需要记住特定关键词句式。
2. As a 餐食计划用户, I want 简报完成后说"我喜欢清淡的餐食"时继续进入简报补充, so that 偏好不会丢失也不会被误当成一次单餐推荐。
3. As a 餐食计划用户, I want 简报完成后说"我喜欢中餐，上班做饭时间有限，希望烹饪时间短一些"时菜系与烹饪时长被理解, so that 生成的计划尊重这些约束。
4. As a 餐食计划用户, I want 补充话术暂时无法理解时得到"已理解什么、还可以补充什么"的枚举指引, so that 我不会被"请先整理需求简报"这类内部术语卡住。
5. As a 餐食计划用户, I want 每次补充后立即看到更新后的简报摘要, so that 我确认新条件已被记录。
6. As a 健康聊天用户, I want 在计划简报会话中说"有什么推荐"这类明确推荐请求时进入单次推荐, so that 明确任务词依然即时生效。

## Implementation Decisions

- **结构化续轮判定（单一实现 + 固定优先级）**：新增共享判定组件，输入为会话状态与当轮文本，输出结构化结果：`briefActive`（计划简报会话是否活跃）、`activeSide`（MEAL | EXERCISE | BOTH | NONE，仅 COMPOSITE 有意义）、`escape`（`RECOMMEND` | `ALTERNATIVE` | `DOMAIN_OR_ROUTINE` | `NONE`）、`reason`（命中哪一优先级）。意图链的模型前续轮、模型后修正、编排器简报门槛三处复用同一实现；判定落在意图包内，不建第二套路由状态机。**裁决优先级为固定合同，同一输入命中多个条件时按序唯一裁决，三个调用点不得各自覆写**：风险阻断 > 明确领域切换/作息提问 > 明确替代/换一批 > 明确普通推荐逃生口 > 简报生命周期（GENERATED/PAUSED 不捕获）> activeSide 归属 > 字段解析。
- **逃生口**：① 明确普通推荐请求词（合并现有两份漂移副本为一份共享清单：推荐、吃什么、看看今晚等，不含"计划/安排"时生效）→ `RECOMMEND`，放行单次推荐；② “换一批/替代推荐/再来一批”→ `ALTERNATIVE`，保持 ADJUST 通道并豁免预检；③ 明确切换领域或作息事实提问 → `DOMAIN_OR_ROUTINE`，交完整意图链（保留跨域隔离语义）。其余场景交完整意图链，新会话模糊短句仍降级为 OTHER + CHAT。
- **简报会话生命周期（含生成侧落点）**：会话状态新增 `_meta.briefLifecycle = {"MEAL":"OPEN|PAUSED|GENERATED", "EXERCISE":"OPEN|PAUSED|GENERATED"}`，随会话 JSON 持久化；COMPOSITE 会话激活两侧，综合生成把两侧置为 GENERATED；旧会话 JSON 缺字段时按“对应计划简报有内容且 task 为 PLAN 即 OPEN”推导，缺少内容则为无状态，无库表迁移。转移规则：进入简报处理器/澄清 → OPEN；显式切换其他领域 → PAUSED（**暂停 ≠ 关闭**，显式计划词恢复 OPEN）；**对应范围生成成功 → GENERATED**（简报保留展示，briefActive=false）；MEAL-only/EXERCISE-only 生成只关闭对应侧，COMPOSITE 生成才同时关闭两侧；新开会话/重置 → 状态清空。`briefActive` = 该范围简报有内容且生命周期为 OPEN。
- **生成服务的关闭职责与耐久幂等**：训练、餐食、综合三个生成入口在计划写事务中以 `operation=GENERATE_<scope>`、`userId + requestId`（requestId 对同一用户全局唯一）写入既有 `health_plan_write_request`（响应快照包含 planId、scope、sessionId、generationNotes）；该记录与 weekly plan/版本快照同一事务提交。生成入口先查该记录，命中时恢复既有响应，再只执行一次“补偿式”生命周期回写，不重新生成计划；同一 requestId 被不同 session/scope 使用时返回幂等冲突，不创建计划。计划已提交但会话回写失败时请求返回 5xx；重试命中生成写记录，重新以行锁合并回写生命周期，成功后返回原响应。Trace 仅作诊断，不能作为生成幂等唯一来源；任何计划写入、幂等记录或会话回写失败均不得留下“已生成但无可恢复记录”的状态。
- **会话并发写入合同**：简报更新和生成关闭都必须经过 `HealthSessionService` 的事务性行锁更新：读取 `FOR UPDATE` 的最新 JSON，只合并目标字段/生命周期，再写回；不得用生成入口的旧快照覆盖新简报。单实例测试可复用现有会话锁，多实例语义以数据库行锁为准。MEAL/EXERCISE 的生命周期更新必须是幂等的，已 GENERATED 不得被旧请求回写为 OPEN/PAUSED。
- **综合简报侧归属规则**（由 `activeSide` 表达）：NONE（两侧皆空）→ 一律写入餐食侧（默认收集顺序餐食优先）；无前缀且餐食未完整 → MEAL；餐食完整且训练未完整 → EXERCISE；两侧都完整 → BOTH 状态下无前缀的模糊补充不猜测归属，返回两侧摘要并要求"餐食：/训练："前缀；**显式侧前缀（"餐食/饮食…"或"训练/健身…"）优先级最高**，允许跨侧补充或修改（与 #102"修改一侧只更新该侧并重新展示生成入口"一致）。侧归属只决定写入目标，不参与领域/任务路由。
- **关键词清单分类处理**：路由类清单（计划续轮词、两份推荐请求词副本、简报续轮词、综合简报回复词）收敛进共享结构化判定，副本删除；侧归属词与字段解析词（餐食/训练输入词、无关输入判定等）保留其内容识别职责，但收编进结构化判定的子结果或简报服务内部，**不得参与领域/任务路由**。验收标准是"领域与任务路由入口唯一"，不是机械清点方法被删。
- **编排器简报门槛等价改写**：现有"文本匹配计划词或命中续轮词"的前置检查由共享判定替代；显式计划词（含"计划"等）仍直接进入简报。计划任务兜底（无活跃简报且无计划词）预期只剩模型幻觉场景，文案改为可行动指引。
- **未支持菜系的确定性提取机制（不依赖模型、不参与路由）**：受支持集合的唯一事实来源仍是归一器别名表；简报层新增一个受限的确定性“菜系意图”解析器，输入范围仅两种形态——① 显式标签形态：“菜系：X / 菜系是 X / X 菜系”；② 封闭超类词表（中餐、中式等极小封闭清单，明确标注“非库标签”，可在自然句中出现）。解析器先剥除否定范围（“不喜欢/不要/避免 X”不得写入正向偏好），再按中文标点和“和/或/以及”分隔候选值；解析出的值先过别名表：命中 → 受支持菜系（可过滤）；未命中但在上述两种形态内 → 原值写入菜系字段并登记未支持集合，回应附当前可选菜系列表；两种形态之外 → 不解析，走 INVALID 枚举指引。**该解析器必须在 `isUnrelated`/`looksLikeMealInput` 之前运行；可选偏好命中本身足以使输入进入餐食简报处理器。** 输出只写 `MealPlanBrief`，不进入通用会话槽位、不参与领域/任务路由；模型 rawSlots 中未被别名表收录的未知值必须丢弃，只有该解析器能产生未支持原值。
- **单选/多值冲突语义（对齐既有难度单选模式）**：菜系与便利性为单选——一次输入解析出多个值时：字段已有值且无"换成/改为"语义 → 保留已有值并提示"只能选择一个"；字段为空且恰有一个受支持值（其余为未支持值）→ 采用受支持值、其余登记未支持并说明（如"中餐、川菜"→ 采用川菜、记录中餐）；多个受支持值 → 不猜测，返回可选列表要求重选。口味/营养偏好为多值列表：追加去重；"换成/改为"清除重建。热量目标永不被口味值覆盖。
- **餐食简报可选字段与唯一来源**：`MealPlanBrief` 的稳定 JSON 形状为 `{weekStart, mealTimes, healthGoal, cuisine: string|null, tastePreferences: string[], convenience: string|null, unsupportedPreferences: string[]}`；列表字段始终为数组，未填单值为 `null`，`unsupportedPreferences` 使用稳定键 `field:value` 并去重。健康目标白名单（减脂、增肌、维持健康、均衡）仍写 `healthGoal`；清淡、低油、低盐、高蛋白等写 `tastePreferences`；菜系、便利性直落。`MealPlanBrief` 是计划简报的唯一来源，通用 `slots` 中的旧 cuisine/taste/convenience 只在旧会话且计划字段为空时一次性导入，导入后不再双写。已有热量目标永不被口味值覆盖。**未支持值不参与任何检索/生成过滤**，但在摘要、回复文案、生成 metadata 与计划说明中如实展示。词汇增补：便利性别名补充“烹饪时间短、做饭时间有限、快手菜、没时间做饭→快速”；不新增“中餐”到别名表（走未支持路径）。
- **摘要与指引扩展**：简报摘要展示可选偏好与未支持项；新增"可补充项"输出（字段中文名 + 示例值，仅列未填项；已填项提示可"换成/改为"）。训练、餐食、综合三个简报完成分支的回复文案统一由该输出拼接；INVALID 输入的指引同样使用该枚举。
- **计划候选标签接口**：扩展计划餐食候选记录，新增受控标签字段 `cuisineTags`、`tasteTags`、`nutritionPreferenceTags`、`convenienceTags`（均为列表）；审核库 Provider 从 `meal_item.cuisine/taste/health_goal/convenience` 填充，其中 `nutritionPreferenceTags` 取 health_goal 中除“减脂、增肌、维持健康、均衡”以外的规范值；fixture 种子补充确定性标签表，使两种模式都有可验证基准；挑选器只消费该候选类型。无偏好时挑选行为与现状完全一致（过滤仅在偏好存在时生效），既有 fixture 组合测试不回退。fixture 的 cuisine/taste/convenience 基准新增为：M1 粥汤/清淡/快速、M2 轻食/清淡/快速、M3 粉面/咸鲜/快速、M4 家常/清淡/慢享、M5 家常/清淡/慢享、M6 西餐/番茄味/慢享、M7 轻食/清淡/快速、M8 家常/清淡/快速、M9 粥汤/清淡/快速；新增 nutritionPreferenceTags 基准：M1 []、M2 [低油]、M3 []、M4 [高蛋白]、M5 [高蛋白]、M6 []、M7 [低油, 高蛋白]、M8 [低油, 高蛋白]、M9 [低油]——值域取自归一器规范值；审核库模式是偏好过滤的主验收路径，fixture 表供离线确定性测试。
- **生成过滤语义**：同一字段多值 OR、不同字段 AND；未支持偏好不参与过滤。先按餐次分桶，再应用偏好过滤。某日内任一所选餐次的偏好过滤池为空，或偏好约束下无法形成完整的所选餐次组合时，**该日整天回退**到“绕过偏好、保留餐次/唯一性/热量/多样性约束”的全量池（不做单餐半回退的混合日），其余日期继续偏好过滤；纯热量区间无解但偏好池有候选时沿用既有热量回退且不记偏好未满足。回退日的跨日重复仍受既有跨日软多样性约束，不因回退放宽或收紧。未满足偏好记录粒度为“该日 + 字段:值键”，记录导致偏好池为空或组合失败的受支持偏好；未支持偏好只出现在 `unsupportedPreferences`，与“候选不足回退”分区展示。
- **生成过滤补充合同（v3.2）**：`tastePreferences` 必须按规范值类别逐值映射：口味值只匹配候选 `tasteTags`，营养偏好值只匹配候选 `nutritionPreferenceTags`；同一字段内多值 OR，不同偏好值/字段之间 AND。边界例：`{清淡, 高蛋白}` 要求同一候选同时命中 `tasteTags=清淡` 与 `nutritionPreferenceTags=高蛋白`，不能把两个候选字段合并后按 OR；未满足记录仍按 `字段:值` 粒度记录。
- **fixture 标签措辞澄清（v3.2）**：上条 fixture 标签表中的 cuisine/taste/convenience 是为 M1-M9 **新增**的确定性基准，并非声称当前种子已有这些标签；nutritionPreferenceTags 同样为新增测试基准。
- **三处可见的字段形状**：生成 metadata 写入结构化 `generationNotes = { unsupportedPreferences: ["cuisine:中餐"], fallbacks: [{date: "YYYY-MM-DD", mealTimes: ["早餐"], unmetPreferences: ["cuisine:川菜", …]}] }`（所有数组非 null，日期为计划时区的 ISO 日期）；`PlanView` 新增 `GenerationNotes generationNotes` 字段，从 metadata 透传解析，版本快照的 `resource_snapshot_json.generation.generationNotes` 与计划详情 API 都返回。新增 `GET /api/v1/health/plans/{planId}/versions/{versionNo}` 返回对应版本的同形状 PlanView；旧计划或缺少 metadata 时返回空对象。计划页在头部说明区（周/范围/状态行下）渲染未支持偏好与按日回退说明，两区分明示。聊天侧简报“可补充项”响应字段结构为 `{key, label, examples: string[], filled: boolean}` 列表（计划侧三个领域通用；推荐预检沿用既有 optionalSlots 字段不变），并随既有简报对象下发可选偏好与未支持项。
- **推荐前预检**：触发条件从“候选数大于 2”改为“候选非空 且 任务非 ADJUST 且 `escape` 非 ALTERNATIVE 且当前请求的确认指纹未命中”；确认指纹为 `domain + task + 规范化有效槽位 + resourceProvider.resourceVersion` 的稳定 SHA-256，写入会话 `_meta.recommendationConfirmationKey`，槽位、领域、资源版本、替代推荐或新会话变化都会使旧确认失效。旧会话只有布尔确认而没有指纹时按未确认处理。预检内容保持“已确认条件 + 可补充槽位（仅未选项）+ 两个动作”。**按钮规范标签以 ADR-0016 为准：推荐侧“开始推荐/补充”，计划侧“开始生成/补充”**；现有“为我推荐/继续补充需求”实现标签与确认短语清单同步收敛到规范标签，自动化测试与浏览器证据断言规范标签。
- **推荐预检实现补充合同（v3.2）**：确认指纹采用 UTF-8 canonical 输入串 `domain=<值>\ntask=<值>\nslots=<按键名字典序、列表去重并按规范值排序的 canonical JSON>\nresourceVersion=<值>`，空值显式编码后计算 SHA-256；前端“开始推荐”必须发送同名确认短语，后端确认清单必须包含该短语（旧别名仅作兼容）。
- **前端**：计划"补充"动作把可补充项渲染为可点 chip，点击把"属性名："参考输入填入输入框并聚焦；聊天页计划简报摘要组件渲染新增偏好与未支持项（不只依赖 speechText）；计划页渲染 generationNotes（见上）；预检与生成按钮语义不变；不做框架级重构。
- **会话兼容**：新字段（简报可选偏好、未支持集合、生命周期）随会话 JSON 持久化；旧会话 JSON 缺字段按空/推导读取，无数据库迁移。
- 不修改 weekly plan 生命周期（V17-V20 状态机与迁移语义），仅新增聊天简报生命周期字段；不修改资源 Provider/Reader 读取边界、旧饮食链路或既有确认/启用/编辑操作的幂等语义；生成入口允许在同一张写请求表增加 `GENERATE_<scope>` 幂等操作；不引入新的意图状态机或检索系统。

## Testing Decisions

- **最高接缝沿用 `POST /api/v1/health/chat` 完整轮次测试**（上一轮规格确立的接缝，本轮不新增接缝）：断言 responseType、domain、task、phase、missingSlots、actions、speechText 标记片段、可补充项字段与简报字段值；**结构化判定的测试必须断言判定原因（escape 类型、activeSide、briefActive），不只断言最终 domain/task**；不断言内部关键词清单，不锁定易变模型措辞。
- 简报服务单测沿用既有简报服务测试先例：字段归属映射（热量目标与口味互不覆盖）、菜系意图解析器（标签形态/超类词表/范围外拒绝/否定范围剥除）、单选冲突（"中餐、川菜"采用川菜并记录中餐；已有值无改成语义时保留并提示）、未支持偏好登记与展示、摘要含可选偏好、可补充项枚举、INVALID 指引、社交短句行为。必须用原始失败句验证可选偏好在 `isUnrelated` 之前被提取，且模型 rawSlots 的未知值不会绕过受限解析器。
- 生命周期与生成回写测试：三个生成入口成功后对应范围转 GENERATED（最高接缝或生成服务接缝）；MEAL-only/EXERCISE-only 不误关另一侧，COMPOSITE 同时关闭两侧；幂等重放不改变状态且只返回一份草稿；计划写入/幂等记录/会话回写任一步骤失败时事务与恢复路径符合合同，重试经 `GENERATE_<scope>` 写幂等最终一致。补充并发测试：聊天补充与生成关闭同时发生时不得丢失简报字段，已 GENERATED 不被旧请求覆盖。
- 综合侧归属矩阵（最高接缝）：NONE/焦点侧/BOTH 澄清/显式前缀跨侧修改，各断言写入目标侧与判定原因。
- 生成侧沿用确定性生成/挑选器测试先例：两种 Provider 模式的标签填充（fixture 按确定性标签表断言，含低油/高蛋白营养标签）、偏好过滤命中候选 ID、同字段 OR/跨字段 AND、**整天回退边界例**（偏好 {家常+快速} 下某日早餐池为空 → 该日整天回退但仍只生成所选餐次、其余日照常、说明带日期）、偏好交集无法形成完整餐次时整天回退、纯热量回退不记偏好未满足、跨日软多样性在回退日不放宽、无偏好行为不变、综合计划偏好端到端。
- 前端沿用 node 模块测试先例：可补充项 chip 渲染与点击填充、聊天页计划摘要含新增偏好字段、计划页 generationNotes 两分区渲染。
- **持久化与可见性回归（必须覆盖）**：新旧会话 JSON 序列化/反序列化往返（含 `_meta.briefLifecycle`、`_meta.recommendationConfirmationKey`、新字段与未支持项）；未支持偏好在会话重启后保留；generationNotes 同时存在于生成 metadata、版本快照、计划详情 API 与版本详情 API，并在计划页展示；旧计划缺 metadata 时返回非 null 空对象。
- **推荐前预检真实 API 回归**：在档案存在的前提下于 Controller 层断言候选 1/2/3 个时均先预检、确认后直出、ADJUST 直出。
