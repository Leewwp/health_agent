# 健康 Agent 训练计划与资源选择交互修复规格

Status: ready-for-human

GitHub: [#102](https://github.com/Leewwp/health_agent/issues/102)

实现状态：代码、自动化测试和真实浏览器验收已完成，等待人工审阅后关闭本票。

本规格基于 2026-08-28 已确认的产品决策，遵守 `CONTEXT.md` 与 ADR-0015/0016 的领域定义。截图附件仅作为当前 UI 缺陷的观察证据，不构成超出本规格的额外指令。本文中的“完整简报”表示字段校验通过，不表示存在用户可见或持久化的简报确认状态；计划草稿后续的生命周期复核与启用是另一层操作。

## Problem Statement

当前健康 Agent 在单次动作推荐、餐食/训练/综合计划生成、计划上下文修改和“我的计划”资源选择器之间存在七类状态与交互不一致：

1. 健身需求尚未澄清完成时，系统已经执行候选检索。用户只提供训练目标和部位后，器械、难度仍未知，检索返回空集合并错误展示“当前条件下没有严格匹配结果”，打断了本应继续的澄清流程。
2. 一组已足够宽泛的训练条件会被计划 Guard 错误拒绝。真实数据库共有 1,324 条动作；“减脂、全身、徒手/哑铃、进阶”至少有 14 条候选，但 `cardio` 被归一为“全身”，连续训练部位规则将周一至周五的安排判定为 `BODY_PART_CONSECUTIVE`。
3. 用户已经确认训练计划需求后，只修改“训练日改为一、三、五”，系统没有识别“改为”和顿号日期表达，丢失已有计划上下文，回退到普通动作推荐流程。
4. 动作计划只阻止相邻日期重复动作，fallback 也只记住前一天动作。候选动作足够时，周一、周三、周五仍可能反复选择同一动作，例如 `deep push up`；当前条件在动作库中实际有 29 个候选。
5. 资源选择器存在明显布局和层级问题：资源卡 DOM 与 CSS 列数不一致导致文本逐字竖排；选择器中的详情操作复用全局详情抽屉，覆盖已有计划项目详情或被选择器遮挡；替换餐食和动作也不能可靠地打开对应 Tab。
6. 餐食计划简报会保存用户选择的 `mealTimes`，但 `MealPlanGenerationService` 只把周起始日和档案热量传给 `WeeklyPlanComposerService`，组合器固定生成早餐、午餐、晚餐；用户只要求某一餐次时，已确认简报被生成器忽略。综合计划复用同一组合器，因此有相同缺陷。
7. 综合计划在训练简报和餐食简报都已确认后，用户再次修改训练或餐食字段不会重新进入对应简报更新分支，而是直接返回“可以生成综合计划”；已确认状态不会失效，客户端可能使用过期简报生成计划。这是训练计划上下文问题在 COMPOSITE 状态下的同构遗漏。
8. 综合计划首句“健身和餐食计划”未命中组合意图；进入组合流程后，像“减脂”这样的共享目标又可能被重新推断为健身域，导致餐食子简报被清空或流程跳出。系统缺少有序阶段与共享字段继承规则。
9. 资源详情异步加载时同时保留推荐卡摘要和完整详情，造成两份媒体/内容；动作详情还同时展示整段 `instructionsZh` 与拆分后的 `steps`，形成重复讲解。
10. 计划选择器详情只展示少数字段，未满足资源库完整详情要求；选择器餐食收藏成功后列表仍显示旧状态。资源库详情抽屉的收藏和减少推荐按钮没有绑定到抽屉根节点，点击无效果。
11. 计划时间解析只接受 `HH:mm`，对实际输入的 `HH:mm:ss` 会从秒字段中间截取，产生错误开始时间。

这些问题共同说明：推荐澄清、计划简报、计划生成 Guard、资源详情浏览和资源选择操作没有被建模为清晰的独立状态。修复需要保持现有后端健康资源边界、计划生命周期、匿名会话和前端 vanilla ES Modules，不引入新的产品流程或数据库模型。

## Solution

将健身推荐、计划上下文和资源选择器分别收敛到明确的状态契约：

- 健身单次动作推荐在训练目标、训练部位、器械和难度四项必填槽位完成前，只执行确定性澄清；完整槽位完成后才允许检索，并可进入一次明确的推荐前预览。
- 训练计划不再把训练部位连续性作为阻断规则。用户指定的训练日和部位优先，“全身”可以连续安排。动作候选数量足以覆盖训练日时，一周内动作全局不重复；候选不足时允许复用，但按最少重复原则选择。
- 会话已经处于计划上下文时，能解释为计划字段的输入优先更新现有 `planBrief`，包括“我想练胸”这类部位修改；只有明确的“推荐动作”“推荐餐食”“生成餐食计划”等新任务才切换流程。字段修改后必须重新展示当前简报和“开始生成”入口，服务端在开始生成时重新校验，不保留独立确认状态。
- 资源选择器使用独立的资源详情弹窗。弹窗只浏览内容，不提供“选择此资源”按钮；用户关闭详情后在选择器卡片上自行选择。弹窗支持关闭按钮、点击外部遮罩和键盘 `Esc`，拥有独立滚动并保留选择器状态。
- 替换餐食默认打开餐食 Tab，替换动作默认打开动作 Tab；新增项目固定默认打开餐食 Tab。详情读取失败不阻止用户依据列表卡片选择具有稳定 ID 和合法资格的资源。
- 餐食计划和综合计划生成必须消费已确认的餐次集合；不得把简报中的 `mealTimes` 静默扩大为固定三餐。每日热量按早餐/午餐/晚餐 30/40/30 权重对已选餐次归一化；候选足够时七天内优先换餐，候选不足时允许最少重复且不阻断计划。
- COMPOSITE 上下文中的训练/餐食字段修改必须只更新对应子简报，并重新展示综合简报；两份子简报未同时完整前不得开始生成，不能用隐藏确认状态阻断或放行。

## User Stories

1. As a 健身推荐用户, I want to先完成训练目标、训练部位、器械和难度澄清, so that 系统不会在需求尚未完整时误报没有匹配结果。
2. As a 健身推荐用户, I want每轮只追问仍缺失的健身字段, so that 我可以按自然对话逐项补充条件。
3. As a 健身推荐用户, I want在四项必填条件完成前看不到候选检索结果, so that 推荐不会基于未确认的默认器械或难度。
4. As a 健身推荐用户, I want完整条件完成后看到需求摘要和明确的开始推荐操作, so that 我能决定何时触发推荐。
5. As a 健身推荐用户, I want空结果提示只在澄清完成后出现, so that 追加条件建议代表真实的严格匹配失败。
6. As a 健身推荐用户, I want空结果追加选项保留已有条件, so that 我只需补充一个可用值而不必重新输入整轮需求。
7. As a 训练计划用户, I want使用“全身”作为训练部位, so that 周内连续训练不会被错误拒绝。
8. As a 训练计划用户, I want连续几天训练同一个部位, so that 计划尊重我的实际训练需求而不是强制轮换部位。
9. As a 训练计划用户, I want训练计划覆盖我指定的全部训练日, so that 候选足够时不会因为错误的部位规则生成失败。
10. As a 训练计划用户, I want在有足够候选动作时每天使用不同动作, so that 一周训练具有动作多样性。
11. As a 训练计划用户, I want候选动作少于训练日时仍获得可执行计划, so that 唯一可行动作不会因去重规则导致计划失败。
12. As a 训练计划用户, I want候选不足时重复次数尽可能少, so that 复用是必要时的降级而不是默认排序结果。
13. As a 训练计划用户, I want Agent 输出重复动作时由系统纠正, so that 模型的不稳定输出不会破坏已确认的多样性要求。
14. As a 训练计划用户, I want训练计划继续遵守动作资格、器械、难度、目标、风险和时间约束, so that 多样性不会覆盖安全和可执行性规则。
15. As a 训练计划用户, I want看到生成失败的具体类别, so that 候选不足、Agent 输出非法和 Guard 拒绝不会显示同一条误导文案。
16. As a 计划用户, I want在完整简报后说“训练日改为一、三、五”, so that 系统修改训练计划而不是跳转到普通动作推荐。
17. As a 计划用户, I want使用“改为、调整为、换成、改成”等表达, so that 口语化计划修改可以进入同一计划流程。
18. As a 计划用户, I want使用“一、三、五”“周一、周三、周五”“星期一和星期三”“每周一三五”等日期表达, so that 修改训练日不受固定格式限制。
19. As a 计划用户, I want说“我想练胸”时更新当前计划部位, so that 计划上下文优先于普通推荐意图。
20. As a 计划用户, I want说“推荐胸部动作”时明确开始新动作推荐, so that 我可以主动退出计划上下文。
21. As a 计划用户, I want修改已确认字段后看到新的计划简报, so that 我能核对系统是否正确合并了修改。
22. As a 计划用户, I want修改简报后必须重新查看摘要并再次选择“开始生成”, so that 新条件会在服务端校验后才生成计划。
23. As a 计划用户, I want普通餐食或动作推荐不污染计划简报, so that 不同任务的条件保持隔离。
24. As a 计划用户, I want计划上下文仅在当前会话内延续, so that 新会话不会继承旧计划的隐式条件。
25. As a 计划编辑用户, I want资源卡上的名称和摘要横向正常排版, so that 我可以快速比较候选资源。
26. As a 计划编辑用户, I want替换餐食时选择器自动打开餐食 Tab, so that 我不必手动切换品类。
27. As a 计划编辑用户, I want替换动作时选择器自动打开动作 Tab, so that 我不会误选错误类型的资源。
28. As a 计划编辑用户, I want新增项目默认打开餐食 Tab, so that 新增流程有稳定且可预测的初始状态。
29. As a 计划编辑用户, I want点击候选资源查看完整动作或餐食详情, so that 我可以在选择前核对步骤、营养和来源。
30. As a 计划编辑用户, I want详情浏览不提供自动选择操作, so that 查看信息和选择资源是两个明确的动作。
31. As a 计划编辑用户, I want关闭详情后仍保留当前 Tab、筛选、页码和滚动位置, so that 我可以继续浏览而不丢失上下文。
32. As a 计划编辑用户, I want使用关闭按钮关闭详情, so that 鼠标用户有明确的退出入口。
33. As a 键盘用户, I want按 `Esc` 关闭详情弹窗, so that 不依赖鼠标也能退出浏览。
34. As a 计划编辑用户, I want点击弹窗外部关闭详情, so that 我可以快速返回资源列表。
35. As a 计划编辑用户, I want详情弹窗独立滚动, so that 长步骤和营养内容不会被选择器裁切。
36. As a 计划编辑用户, I want计划项目详情抽屉在打开资源选择器详情时不被破坏, so that 返回后仍能继续编辑原项目。
37. As a 计划编辑用户, I want详情接口暂时失败时仍能选择列表中的合法资源, so that 辅助详情服务故障不会阻塞计划编辑。
38. As a 计划编辑用户, I want资源选择器中的替换和新增状态互不混淆, so that 关闭或返回不会误改已有项目。
39. As a 开发者, I want推荐澄清、计划简报、计划生成和 picker 详情分别有清晰接缝, so that 每个状态可以独立回归而不依赖 DOM 或私有方法。
40. As a 开发者, I want Trace 记录候选数量、去重决策、Agent 输出和 Guard 结果, so that 生成问题可以通过证据定位而不是猜测。
41. As a 开发者, I want既有数据库和计划生命周期保持兼容, so that 修复不产生迁移风险或旧计划状态破坏。
42. As a 验收人员, I want在桌面和移动真实浏览器中验证完整流程, so that CSS、弹层层级和键盘交互不会只在单元测试中被假定正确。

## Implementation Decisions

### 推荐澄清与空结果边界

- 继续使用现有健康聊天编排器作为最高接缝；不新建第二套健身推荐状态机。
- 将 `EXERCISE` 单次推荐的最小推荐槽位定义为 `trainingGoal`、`bodyParts`、`equipment`、`difficulty` 四项。槽位值继续经现有输入归一化和领域字典校验。
- `HealthOrchestratorService` 在健身四项缺失任一项时只调用确定性澄清并持久化当前槽位，不调用资源 Provider，不执行候选过滤，不进入空结果分支。
- 四项完成后才允许候选检索；推荐前预览可以在检索结果可用时展示，但摘要必须反映四项已确定值。
- 空结果追加条件建议只能由“澄清已完成且严格候选为空”触发。追加值必须来自可验证的审核资源选项，保留已有条件，不静默放宽风险或硬约束。
- 餐食和作息推荐的既有最低槽位语义不在本规格中改变。

### 计划上下文与简报

- 继续以会话中的 `HealthSessionState.planBrief` 作为当前计划需求简报，不新增数据库表、跨会话记忆或第二份计划条件。
- 将计划上下文判断放在健康意图修订和编排路由的高层接缝：当前任务是 `PLAN`、当前领域是计划支持领域，且输入可以被 `PlanBriefService` 解释为字段更新时，优先调用简报更新。
- 计划字段更新包括训练目标、部位、器械、难度、目标周、训练日、训练时间和受支持的硬约束。解析失败或无关输入不能覆盖已有简报，应返回确定性提示。
- 明确的新任务词优先级高于计划上下文：至少支持“推荐动作”“推荐餐食”“生成餐食计划”等表达；仅包含“我想练胸”这类字段表达时留在计划上下文。
- 计划字段修改操作保留合并后的简报和缺失字段；响应必须展示更新后的简报与“开始生成/补充”操作，不写入或依赖独立 `confirmed` 状态。
- 综合计划采用有序收集：默认先处理餐食简报，再处理训练简报；当前阶段未完成时，后续追问优先围绕该阶段，避免餐食偏好和训练器械交替追问。用户可随时补充另一侧字段，系统立即合并但不改变当前追问阶段。训练/餐食共享字段（例如“减脂”）可从一侧继承到另一侧；显式输入另一侧独有字段时也必须保留已收集字段，直到两份简报均完整并显示开始生成操作。
- 训练日解析支持中文顿号、逗号、和/及、连续中文数字以及带“周/星期/每周”前缀的表达；重复日期应去重，超出周一至周日或无法解析的表达返回可修改提示。
- 训练时间解析同时接受 `HH:mm` 与 `HH:mm:ss`；秒为 `00` 时归一化为分钟粒度，非零秒明确返回格式错误，不静默四舍五入。
- 简报更新不得把普通餐食/动作推荐槽位写入 `planBrief`；新会话不得读取旧会话简报。

### 餐食计划与综合计划同构审计

- 单次餐食推荐的最低槽位仍是 `mealTime`，其余健康目标、菜系、口味、场景和便利性继续走推荐前预览；本轮没有证据表明必须改为四项全量澄清。实现必须补充回归，证明餐食不会继承健身四项门槛，也不会把餐食槽位写入训练简报。
- `MealPlanBrief.mealTimes` 是用户在简报中整理出的生成约束。生成入口必须将其传入餐食组合器，组合器只生成这些餐次；当只选一个或两个餐次时，日热量预算如何在所选餐次之间分配必须采用确定性、可解释策略，不能由 Agent 临时补齐。餐食计划和综合计划使用同一策略。
- 餐食组合器按日维护资源使用计数：候选足够时七天内优先更换餐食，候选不足时允许按最少重复生成；这是软约束，不因去重不足阻断计划。
- 综合计划必须分别处理训练和餐食子简报：当任一子简报收到可解释字段更新时，只更新该子简报并返回新的摘要；另一子简报保持不变。只有两者再次均完整且周起始日一致时，才显示“开始生成综合计划”操作。
- 综合计划首句必须覆盖“健身和餐食/饮食计划”等组合表达。默认阶段为餐食收集，然后训练收集；用户可交错补充另一侧字段，系统合并后仍保持当前阶段的连续追问。共享目标（例如“减脂”）可从一侧继承到另一侧，但两侧简报仍需分别完整。
- 综合生成仍保持一次性持久化和失败整体回滚；餐食候选为空、训练候选为空、餐训时间冲突或任一 Guard 拒绝时不得留下半成品计划。

### 训练计划候选、Agent Guard 与 fallback

- 继续使用正式审核动作读取接口和 `plan_ready` 候选；本规格不改变资源来源、动作资格字段或数据库 schema。
- 移除训练部位连续性作为阻断校验。可以记录部位连续情况供 Trace 或诊断使用，但不能返回计划生成失败，也不能要求 Agent 自动错开用户指定部位。
- Agent 生成安排必须覆盖简报指定的每一个训练日，动作 ID 必须属于过滤后的候选白名单，日期、时间、时长、器械、目标、难度和风险仍由确定性 Guard 校验。
- 当严格候选数量大于或等于训练日数量时，Guard 要求同一周内动作资源 ID 全局唯一。Agent 输出违反此条件时转入 fallback 或返回稳定的生成错误，不接受可避免的重复。
- 当候选数量小于训练日数量时，允许资源 ID 复用；fallback 按已使用次数升序、优先避免上一训练日相同动作、再按稳定资源 ID 排序，尽量减少重复，同时保证每个指定日期都有项目。
- 候选数量为 1 时，允许每天安排同一动作，不增加针对单候选的特殊排程分支。
- fallback 与 Agent 必须消费同一份当前完整简报和同一批候选，禁止回退到旧的固定日期、固定时间或只使用单一部位字段。
- 生成 Trace 增加候选总数、候选资源 ID、候选部位、训练日数量、Agent 原始选择、去重 Guard 决策、fallback 使用次数和最终生成来源。敏感信息继续遵守现有 Trace 脱敏边界。
- 训练生成事务边界、版本快照、激活流程、风险重检和写入幂等保持现状，不因本次去重或部位规则调整而改变。

### 餐食组合与综合合并

- `MealPlanGenerationService` 和 `CompositePlanGenerationService` 必须从服务端重新读取当前 `MealPlanBrief.mealTimes`，并把餐次集合、候选数量、每日选择结果和热量分配写入 Trace/版本元数据。
- 组合器接收显式餐次参数；固定的早/午/晚窗口只能作为所选餐次的窗口定义，不能绕过用户未选择的餐次。
- 综合生成复用同一餐食组合器和训练生成器，不建立第二套餐食选择或训练上下文逻辑；两条子路径的失败分类在综合 Trace 中保留可区分的 `meal`/`exercise` 来源。

### 资源选择器与详情弹窗

- 继续使用计划页面现有资源选择器作为唯一替换/新增入口，不新建页面或路由。
- 资源卡布局按实际 DOM 使用主体区和操作区两列；主体内容允许缩小，名称和摘要不得因固定缩略图列而逐字换行。
- 在计划页面维护独立的 picker detail 状态和渲染层，不能调用计划项目详情抽屉作为 picker 详情。
- picker detail 弹窗显示资源库返回的完整用户可见字段：餐食的媒体、营养、份量、描述、食材、过敏原、标签、来源和审核状态；动作的实际媒体、步骤（优先于整段讲解）、目标/辅助肌群、部位、器材、难度、类别、动作模式、风险、来源、资格和审核状态。不显示“选择此资源”或减少推荐操作；允许保留一个收藏按钮，收藏状态必须即时更新。用户关闭弹窗后，在原选择器卡片点击“选择”完成替换或新增。
- 弹窗采用独立的固定层级和内容滚动；打开时不销毁 picker 的 Tab、查询、结构化筛选、收藏筛选、页码、资源列表和滚动位置。
- 支持关闭按钮、点击遮罩关闭和 `Escape` 关闭。关闭后恢复触发详情的列表按钮焦点；重复打开不同资源时，异步详情响应不得覆盖当前资源。
- 资源详情加载失败显示可理解的错误状态，但只要列表资源具有稳定资源 ID 且满足当前操作的类型和资格校验，仍允许在列表中完成选择。
- 替换入口将资源类型作为初始 Tab：餐食为 `MEAL`，动作为 `EXERCISE`。新增入口固定初始 Tab 为 `MEAL`，不根据复杂上下文额外推断。
- 原计划项目详情抽屉继续负责查看和编辑已加入计划的项目；两种详情层的状态、关闭、滚动和焦点不能互相覆盖。
- 有异步详情接口时，详情抽屉只渲染一个详情容器：加载期间显示占位，成功后整体替换为完整详情，不保留列表摘要。媒体按实际返回内容选择，避免同一资源的摘要与完整详情重复。动作有 `steps` 时隐藏 `instructionsZh`，无步骤时才回退整段讲解。
- 资源库详情抽屉必须绑定自身根节点的反馈事件委托；收藏与减少推荐沿用服务端接口、乐观更新和失败回滚。浏览页使用稳定客户端 session，聊天详情继续透传真实 session/trace。

### API、持久化和兼容性

- 本次修复不新增数据库表、不改变现有计划状态枚举、不改变健康资源读取边界、不改变旧饮食 API 契约。
- 计划生成请求仍由服务端重新读取最新的 `planBrief`；客户端展示的简报不能作为唯一信任来源。
- 计划字段修改只更新当前会话简报，生成计划仍经过现有健康档案风险 Guard、候选资格 Guard、时间校验、版本和幂等写入。
- 错误码和用户文案应区分“仍需澄清”“严格候选为空”“候选资格不足”“Agent 输出非法”“风险/时间 Guard 拒绝”五类结果。

## Testing Decisions

- 测试优先断言外部行为和领域不变量，不固定 Prompt 排版、私有方法调用次数或具体 HTML 顺序。最高接缝是健康聊天编排器、训练计划生成服务、计划简报更新服务和运行中的计划页面。
- 健身推荐编排测试：目标和部位已填但器械/难度缺失时只返回澄清；补齐四项后才调用候选检索；完整条件的空候选才返回追加选项；追加后原槽位仍保留。
- 计划上下文路由测试：简报完整后的“训练日改为一、三、五”“每周一三五”“星期一和星期三”均更新简报；“我想练胸”更新当前计划部位；“推荐胸部动作”切换动作推荐；字段更新后只重新展示简报并要求再次选择开始生成；普通推荐不污染简报；新会话隔离旧简报。
- 餐食计划上下文测试：简报完整后修改餐次、目标周或餐食目标时，只更新 `mealPlanBrief` 并重新展示生成入口；普通餐食推荐不污染餐食简报；训练字段不改变餐食简报。
- 综合计划上下文测试：两份子简报均完整后分别修改训练字段和餐食字段，均必须回到对应子简报并重新展示综合摘要；另一侧内容保持不变，开始生成前不能使用旧快照。
- 综合计划阶段测试：首句“健身和餐食计划”识别为 COMPOSITE；默认按餐食→训练阶段追问，用户可交错补充；共享目标可继承到另一侧；“减脂”不会把餐食阶段抢成普通训练推荐；两侧均完整后才出现开始生成操作。
- 日期解析测试覆盖周/星期前缀、顿号、逗号、和/及、连续数字、重复日期、非法日期和跨周输入。
- 时间解析测试覆盖 `18:00-19:00`、`18:00:00-19:00:00`、中文时间、非零秒拒绝及半小时粒度 Guard。
- 训练生成测试使用真实规模的候选夹具：14 个候选覆盖 5 个训练日时生成成功且不触发部位连续错误；29 个候选覆盖 3 个训练日时动作 ID 全局不重复；候选不足时允许复用；候选为 1 时每个指定日仍有安排。
- 餐食生成测试覆盖只选早餐、早餐+午餐和三餐三种简报：生成项目的 `mealTime` 集合必须与简报一致，综合计划也必须一致；候选不足时按明确的热量分配策略返回可解释结果或稳定失败，不静默补餐。
- 餐食跨日重复测试验证候选充足时优先更换、候选不足时允许最少重复；该规则为软约束，不因去重不足阻断计划。
- Agent Guard 测试覆盖重复动作、未知动作 ID、非 `plan_ready`、漏日期、越界时间、风险阻断和其他既有规则。训练部位连续输入不得生成 `BODY_PART_CONSECUTIVE` 阻断结果。
- fallback 测试断言同一份简报、候选和时间窗口被消费；候选数大于训练日时无重复，候选不足时重复次数最小且不漏日期。
- Trace 测试断言候选数、候选 ID、去重决策、Agent/fallback 来源、fallback 原因和 Guard 明细可读取，并保持现有脱敏规则。
- 前端行为测试断言资源卡不发生逐字竖排；替换餐食/动作和新增项目的初始 Tab 正确；picker detail 不打开全局详情抽屉；完整字段、媒体选择和动作步骤去重正确；picker 收藏即时更新；资源详情抽屉收藏/减少推荐事件可提交；关闭按钮、遮罩和 `Esc` 都能关闭；关闭后 picker 状态保持；详情加载失败不阻止列表选择。
- 前端测试还应覆盖异步详情竞态：先打开资源 A，再打开资源 B 时，A 的迟到响应不能覆盖 B；关闭后迟到响应不能重新打开或改写弹窗。
- 真实浏览器验收必须在运行中的同源应用执行，至少覆盖桌面宽度和移动宽度：健身澄清四轮、计划简报修改与重新展示、14 候选五日生成、29 候选动作去重、替换餐食、替换动作、新增项目、长详情滚动、遮罩关闭和 `Esc` 关闭。
- 继续运行既有普通 Maven 测试、MySQL 门控和前端行为测试；本次新增测试失败时不得通过修改旧快照或跳过门控掩盖。
- 测试不得要求 Qdrant、真实模型或外部网络才能证明上述核心语义；真实模型 smoke 和 Qdrant 集成保持既有独立门控。

## Out of Scope

- 不实现跨会话的长期训练偏好记忆、用户画像学习或自动把历史计划字段带入新会话。
- 不把“连续训练部位”改成新的建议、警告、恢复日或医疗规则；本规格只移除其阻断作用。
- 不新增训练动作处方、重量、恢复周期、医疗康复建议、竞技训练周期或效果承诺。
- 不改变餐食推荐的最低槽位、餐食 RAG、Qdrant、作息事实和健康风险规则的其他语义。
- 餐食跨日多样性与单/双餐热量分配遵循文档末尾已确认的产品决策，并在 MEAL/COMPOSITE 生成中保持一致。
- 不新增数据库表、资源类型、计划状态、API 路由或前端框架；不迁移到 React/Vue/Vite/Node 构建链。
- picker 详情弹窗不加入选择、减少推荐、编辑、删除或计划保存操作；允许保留收藏按钮。资源库详情抽屉继续提供收藏和减少推荐，计划保存仍由原编辑流程完成。
- 不重写全站视觉系统、计划时间网格、计划生命周期、版本快照、激活逻辑或并发幂等机制。
- 不实现 SSE、WebSocket、后台队列、Redis 分布式锁、多实例调度或新的模型供应商。
- 不以截图像素复制为目标；只修复截图中能证明的布局、层级、滚动、焦点和交互缺陷。

## Further Notes

- 已确认的领域定义已写入 `CONTEXT.md`，联动取舍记录在 ADR-0015。本规格是实现 issue tracker 中本批修复的执行合同。
- 推荐实现顺序为：先修复健身澄清门槛，再修复计划上下文路由和简报解析，然后修复候选去重与部位 Guard，最后重构 picker detail modal 并进行真实浏览器验收。这样可以先稳定后端状态，再验证前端不会掩盖后端路由错误。
- 现有工作树包含大量用户未提交修改。实现时只能围绕本规格涉及的模块增量修改，不能回滚或覆盖无关改动。
- 完成标准不是“某个示例对话通过”，而是上述状态边界、候选数量边界、详情层级边界和错误恢复边界均有自动化证据，并在桌面与移动真实浏览器中可重复执行。

## 已确认产品决策（2026-08-28）

1. 餐食简报只选择一个或两个餐次（例如早餐，或早餐+午餐）时，生成器只生成所选餐次，并按所选餐次归一化权重分配每日热量。
2. 餐食候选足够时，七天内优先更换餐食；候选不足时允许重复，并按最少重复原则选择。该规则是软多样性约束，不因去重不足单独阻断计划。

3. 综合计划默认按餐食简报、训练简报的顺序收集；用户可交错补充，当前阶段追问保持连续。餐食与训练的共享目标等字段可以互相继承，但两侧均完整后才显示开始生成。
4. 详情接口存在时只显示完整详情，不保留摘要副本；动作有拆分步骤时只显示步骤。媒体按实际返回内容选择，餐食通常显示静态图，动作通常显示动图。
5. 计划时间接受秒为 `00` 的 `HH:mm:ss` 输入并归一化；非零秒拒绝。

上述决策同时适用于 MEAL 和 COMPOSITE 生成；#102 已完成实现收口，Issue 在人工审阅前保持 OPEN。
